## 带着项目问题读原理

### 你最终要交付的业务

用户登记一台设备，提交巡检，立即拿到任务编号。后台执行模拟检查，保存事实，生成不可变报告；AI 根据事实和知识解释问题；用户随后查询报告，收到通知。系统更新版本时，要让已有任务继续运行，数据不丢，失败能查，必要时能退回旧版本。

一条成功请求并不能证明这个系统交付完成。你还要回答：第二次点击会不会创建两份任务？进程在执行中退出会怎样？数据库变慢时请求会积压在哪里？新版出错后旧版能不能读取新版写入的数据？

~~~mermaid
flowchart LR
  U[用户或客户端] --> N[Nginx 或集群入口]
  N --> A[Go API：认证、校验、业务]
  A --> D[(关系数据库：设备、任务、报告索引)]
  A --> C[(Redis：缓存)]
  D --> O[Outbox 发布器]
  O --> Q[消息系统]
  Q --> W[后台 Worker]
  W --> D
  W --> E[Eino 分析流程]
  E --> M[假模型或获准模型]
  W --> S[(报告正文或文档存储)]
  A -.日志、指标、追踪.-> V[可观测平台]
  W -.日志、指标、追踪.-> V
~~~

图中的组件逐步引入。早期报告正文可以存关系数据库；学习 MongoDB 时再做存储对照实验。单机先用进程，后来用 Compose，再学习 Kubernetes。Redis Streams、RabbitMQ、Kafka 分别做对照实验，业务主线只选一种任务传递实现，避免同一事件被三套队列同时处理。

### 开发与运维其实在看同一条链

| 环节 | 开发要解决 | 运维要能判断 |
|---|---|---|
| API | 参数、权限、返回值、错误 | 端口、证书、超时、错误率 |
| 数据库 | 约束、事务、查询、并发更新 | 慢查询、锁等待、连接数、恢复 |
| 缓存 | Key、TTL、失效、一致性 | 命中率、内存、淘汰、热点 |
| 队列 | 发布、消费、幂等、重试 | 积压、最老消息、消费者故障 |
| 微服务 | 合同、截止时间、身份传递 | 服务发现、连接、重试风暴 |
| AI | 输入、证据、工具边界、输出校验 | 延迟、配额、成本、模型故障 |
| 发布 | 兼容旧客户端和旧数据 | 放量、指标、止损、回滚 |

“中间件”有两种常见含义。HTTP 中间件是一段包在处理函数外面的代码；Redis、数据库、消息队列是独立运行的基础服务。会写认证中间件，与会运维 Redis，是两种不同能力。


### 两种能力各需要什么作品

开发成果：接口合同、业务代码、数据约束、错误处理、权限测试、并发与幂等测试。  
运维成果：可重复部署、配置说明、指标面板、日志、调用链、恢复记录、灰度与回滚演练。  
共同成果：用户能完成的业务流程，以及故障时可解释的行为。

先完成 Go+关系数据库单机闭环，再加缓存、队列与观测，然后 Linux/Nginx/Compose，最后 Kubernetes。MongoDB、RabbitMQ、Kafka 可分开做对照，证明能力时标清哪套真正用于业务主线。

### 综合故障练习清单

| 编号 | 教学故障 | 证据 | 通过表现 |
|---|---|---|---|
| F01 | 同时提交相同幂等请求 | 结果、约束、任务数 | 一个业务任务 |
| F02 | 两事务抢同一记录 | 锁时序、SQL、事务状态 | 解释阻塞并安全恢复 |
| F03 | 报告列表数据增长 | 计划、扫描量、延迟、结果 | 优化有证据且结果不变 |
| F04 | Redis 不可用 | 超时、回源量、错误率 | 有界降级 |
| F05 | Worker 提交后 ACK 前退出 | 重投、唯一结果、消费记录 | 不丢结果、不重复副作用 |
| F06 | 消息格式错误 | 重试次数、死信、审计 | 有出口，健康任务继续 |
| F07 | AI 引用伪造证据 | 校验错误、事实 ID | 不保存为有效分析 |
| F08 | Nginx 上游端口错误 | 入口错误、地址、直连检查 | 定位代理与应用边界 |
| F09 | Pod 探针或标签错误 | Events、EndpointSlice、日志 | 单点修复后恢复 |
| F10 | 新版持续报错 | 新旧指标、灰测、发布记录 | 停止放量并兼容回退 |
| F11 | 恢复教学数据库 | 恢复点、校验、耗时 | 数据符合恢复目标 |
| F12 | 跨租户访问缓存/RAG | HTTP、缓存、检索结果 | 均不泄漏数据 |

每次只注入一个故障，先预测再操作。记录“输入与版本→预期→实际→证据→根因→修复→回归→未验证边界”。没有运行的写未验证，不因写了配置就勾完成。

### 语法在开发与运维场景中反复出现

| 知识 | 第一次 | 第二次 | 第三次 |
|---|---|---|---|
| 参数与返回值 | greet | HTTP 处理器 | RPC/模型组件 |
| 结构体与标签 | 设备 JSON | SQL/ORM | 消息 schema、配置 |
| 指针与零值 | 可选字段 | false、NULL | 新旧版本兼容 |
| 接口与依赖 | http.Handler | repository/fake | AnalysisService |
| error 与上下文 | 输入校验 | SQL/RPC 错误 | 日志、追踪、告警 |
| defer 与释放 | 文件/Body | Rows/事务/锁 | 优雅退出 |
| context | 请求取消 | RPC/数据库预算 | Worker、模型、关闭 |
| 并发与同步 | goroutine/map | 条件更新、幂等 | 多副本、租约、恢复 |
| 版本意识 | go.mod | 数据与消息 | 镜像、灰度、回滚 |

忘了 := 就回到变量练习；会语法却不知事务范围，就画写入时序。不同层的问题用不同练习解决，不把所有卡住归结为“基础太差”。

### 怎么判断到了能干活的程度

初级可交付：独立完成小接口，知道参数来源、错误出口、数据落点，有验证。  
单机可维护：部署服务，判断入口、进程、数据库、队列哪个环节故障，按备份恢复。  
团队可迭代：解释兼容性，完成灰度与回滚演练，留下可复现证据。  
进阶：在容量、成本、一致性、恢复时间之间说明选择，针对实际瓶颈优化。

逐步达到这些行为，不以看完所有名词作为毕业标准。

## 把例子接回现有项目

选择一套实际业务主线技术组合，MongoDB/RabbitMQ/Kafka等对照方案注明用途和启用配置，不能同时重复处理同一副作用。交付启动、配置、版本、验收、备份恢复、告警排查与灰度回滚说明；按讲义F01–F12逐项记录结果，未做的明确未验证。仅教学环境，不代表真实上线授权。

### 输入如何走到结果

另一位学习者按文档启动项目，完成一条正常流程并复现指定故障与恢复。

### 分步动手

1. 先固定实际采用的组件和版本，不把所有对照中间件强行装在一起。
2. 重跑基础闭环与各类故障，整理一个可复现证据目录。
3. 按交接文档从干净教学环境恢复并运行，记录仍需人工或真实环境确认的部分。

### 读完后检验是否理解

先口述本题输入、需要改变的模块、权威数据在哪里、失败怎样被发现，再去 [需求与验收](README.md) 实现。讲义配置和表名是示意，先核对已有项目再使用；一处知识卡住可以单独练小片段，业务验收仍以实际运行证据为准。

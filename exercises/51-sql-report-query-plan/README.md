# 51 · 让报告列表数据多了也能解释性能

## 业务为什么需要它

报告积累后列表变慢，用户需要稳定地查看最近报告。

## 这次做成什么

优化已有报告列表的一种固定查询形状。

## 具体需求

在相同隔离库生成可重复的合成数据，固定租户/状态过滤和 created_at、id 稳定排序。记录 SQL、执行计划、扫描量与耗时，选择合适联合索引；深分页对照游标方案。保留租户隔离和字段合同，不能以少返回数据来伪造优化。

## 输入与结果

同一租户最近20份 ready 报告：优化前后返回同一组 ID、相同顺序。

## 今天从这里动手

1. 先建立慢查询基线，避免只有两行数据。
2. 按讲义阅读计划，再只改一处索引或查询。
3. 热/冷缓存条件分开记录，并跑其他租户及空列表回归。

## 怎样算完成

- [ ] 保存相同规模与分布下优化前后的计划及测量方法。
- [ ] 结果、权限和排序稳定；相同时间的记录不随机换序。
- [ ] 说明索引写入代价与游标分页不能任意跳页的限制。

## 带着项目问题读原理

### 先用业务解释对象

| 对象 | 声明的目标 | 在本业务中 |
|---|---|---|
| Pod | 共同调度与运行的一组容器 | 一份 API 实例 |
| Deployment | 无状态实例数量与版本滚动 | 维护 2 份 API |
| Service | 稳定访问一组后端 | 按标签找到 API Pod |
| ConfigMap | 非敏感配置 | 日志级别、功能参数 |
| Secret | 敏感数据分发对象 | 数据库凭据引用 |
| Job / CronJob | 一次性任务 / 定时触发 | 教学迁移、定期检查 |
| PVC / PV | 存储申请与底层卷 | 需要保留的数据 |
| StatefulSet | 稳定身份与存储关联的副本 | 有状态工作负载 |
| Namespace | 资源与管理范围 | 教学环境隔离 |

控制器持续比较目标与实际，再创建或替换对象。Deployment 维持 2 个 Pod，不代表两个都能正确处理请求；Service 找标签，不会替你修复业务。StatefulSet 也不自动解决数据库备份、复制和升级。

集群网络涉及节点、CNI、DNS、Service 转发与入口控制器。NetworkPolicy 是否生效取决于网络实现及配置。先用 ClusterIP 和本机端口转发验证，再学习外部入口，可以减少最初的排障层数。

### YAML 是对象描述，缩进也有含义

以下为教学 Deployment 模板。image 的占位 digest 必须替换；应用须先实现 /livez、/readyz，监听容器内 8080。它用于阅读和后续实验，不是已部署资源：

~~~yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inspection-api
  namespace: go-practice
spec:
  replicas: 2
  selector:
    matchLabels:
      app: inspection-api
  template:
    metadata:
      labels:
        app: inspection-api
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example.com/inspection-api@sha256:<替换为真实digest>
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "256Mi"
          readinessProbe:
            httpGet:
              path: /readyz
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /livez
              port: 8080
            periodSeconds: 10
~~~

metadata 标识对象；spec 描述目标；selector 与 Pod 标签匹配；template 是创建 Pod 的模板。100m 是 0.1 CPU 的请求量，128Mi 是内存数量；这里数字仅为例子，实际用测量设定。

requests 影响调度与资源分配；CPU limit 可能导致节流，内存超限可能出现 OOM 终止。把 limits 拉高不是解决泄漏，把 requests 写小也不会让实际需求消失。[Kubernetes 资源管理](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)。

### 健康检查的三种问题

startup 判断是否已完成启动；readiness 判断是否适合接收流量；liveness 判断是否需要重启。readiness 失败通常使实例退出正常流量后端，liveness 连续失败达到阈值可触发重启，startup 为慢启动提供保护。[Kubernetes 探针](https://kubernetes.io/docs/concepts/workloads/pods/probes/)。

若数据库短暂失败就让所有 API 的 liveness 失败，可能引发全体重启。readiness 也要按核心依赖和降级能力设计，避免无关依赖故障把所有入口下线。业务产生错误时探针不一定发现，仍需业务指标。

Secret 的 base64 表示不等于加密；还需存储保护、RBAC、最小挂载与轮换。能创建工作负载的权限也可能间接获取命名空间中的秘密，要按实际能力审视权限。[Kubernetes Secret 最佳实践](https://kubernetes.io/docs/concepts/security/secrets-good-practices/)。

### 入口组件分清产品与项目

Nginx 软件、Kubernetes Ingress 资源和名为 ingress-nginx 的社区控制器不同。官方公告说明社区 ingress-nginx 于 2026 年 3 月退役；本课程不把它当新环境默认选型。先理解 Service、Gateway API/Ingress 合同，再核实所选控制器维护状态与功能。[Kubernetes 官方公告](https://kubernetes.io/blog/2026/01/29/ingress-nginx-statement/)。


## 把例子接回现有项目

使用 go-practice 命名空间和固定镜像，配置 Deployment、Service、资源请求、探针、终止预算及必要配置引用；先通过端口转发验证，不急于安装入口控制器。有状态依赖沿用已验证教学环境并核对连接预算，不能给两个 Pod 各建独立事实库。

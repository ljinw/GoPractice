## 与本题相连的原理和工程做法

### 先确定权威来源

本业务中数据库保存报告事实，Redis 保存可重建的读取副本。缓存命中返回更快，缓存丢失时能从数据库恢复。任务唯一记录、尚未发布的事件不能只依赖可随时淘汰的缓存。

常见 cache-aside 流程：先做权限判定→读缓存→未命中读数据库→回填缓存→返回。Key 可以包含 tenant、report_id、schema_version，避免不同租户或不同格式碰撞。报告权限变化时，即使正文不可变，也要确保权限检查没有被旧缓存绕过。

String 可保存序列化对象；Hash 适合字段集合；Set 处理去重集合；Sorted Set 表达带分数排序；Streams 支持事件记录和消费者组。数据类型选择应由操作需求决定，不是全部转换成字符串最简单就结束。

### 更新后为什么还会读到旧值

如果先写缓存、数据库写失败，就出现缓存比事实“更成功”。常见做法是数据库提交后删除缓存，但删除失败或并发回填仍可能留下旧值。需要按业务容忍度组合 TTL、重试删除、版本化 Key、事件失效和校验。

一个具体竞态：读请求 A 没命中，读到旧数据库值；写请求 B 提交新值并删缓存；A 随后把旧值回填。这说明“写库后删缓存”不是严格一致性的数学保证。强一致读取可直读权威库；不可变报告用版本 Key 可以简化问题。

不要把延迟双删当成无条件正确的秘诀；它依赖时序假设，网络和任务暂停可能打破假设。先定义“允许旧多久”，再选择机制。

### 三种常见压力问题

| 问题 | 业务表现 | 可选处理与代价 |
|---|---|---|
| 穿透 | 大量查询不存在的报告，每次打数据库 | 输入校验、短时空值缓存、布隆过滤；需处理新建数据和误判 |
| 击穿 | 一个热门 Key 失效，大量并发回源 | 请求合并、受控互斥、提前刷新；等待和失败要有限 |
| 雪崩 | 大量 Key 同时失效或 Redis 故障 | TTL 抖动、回源限流、容量预案、降级；不能无上限压数据库 |

同进程 singleflight 只合并同进程请求，多个实例还会分别回源。缓存故障后可以回数据库，但必须考虑数据库能承受多少额外流量。必要时返回受控的暂时不可用，比把整个系统拖死更可解释。

### 运维要区分到期与淘汰

TTL 是按时间失效；eviction 是达到内存限制后按策略移除键。配置不同策略会影响哪些键可被淘汰，noeviction 下部分写入可能报错。[Redis 内存淘汰](https://redis.io/docs/latest/develop/reference/eviction/)。

监控命中率、内存、淘汰数、延迟、连接数、热点大 Key、复制延迟。缓存与可靠任务流最好隔离资源及策略：缓存可以丢，但消息保留和恢复合同不同。RDB/AOF 以及复制的耐久性要按配置与故障模型验证，不能只因为“Redis 有持久化”就宣称不丢消息。

## 业务为什么需要它

Running 但业务不可访问时，需要按证据定位，而不是反复删 Pod。

## 这次做成什么

定位并修复一次探针配置导致的不可用。

## 具体需求

只在教学环境把一个版本的 readiness 路径改错，保持应用本身正常；通过 Events、Pod状态、日志、EndpointSlice和直接请求确认原因。修复配置后验证流量恢复。资源/HPA/PDB先在讲义梳理，本题不把所有集群故障一次实现。

## 输入与结果

API直连200，Service没有该Pod可用后端；探针路径修正后恢复。

## 今天从这里动手

1. 先记录健康版本的Pod与EndpointSlice。
2. 只改探针路径，依次检查事件、直连和Service。
3. 恢复正确配置，验证任务闭环而非只看Ready绿色。

## 怎样算完成

- [ ] 证据能排除应用崩溃，明确失败在readiness检查。
- [ ] 修复后后端集合与请求恢复，没有凭删除存储掩盖问题。
- [ ] 知道资源节流/OOM与探针失败是不同证据，保留回归记录。

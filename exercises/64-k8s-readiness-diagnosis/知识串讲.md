## 带着项目问题读原理

### 健康检查的三种问题

startup 判断是否已完成启动；readiness 判断是否适合接收流量；liveness 判断是否需要重启。readiness 失败通常使实例退出正常流量后端，liveness 连续失败达到阈值可触发重启，startup 为慢启动提供保护。[Kubernetes 探针](https://kubernetes.io/docs/concepts/workloads/pods/probes/)。

若数据库短暂失败就让所有 API 的 liveness 失败，可能引发全体重启。readiness 也要按核心依赖和降级能力设计，避免无关依赖故障把所有入口下线。业务产生错误时探针不一定发现，仍需业务指标。

Secret 的 base64 表示不等于加密；还需存储保护、RBAC、最小挂载与轮换。能创建工作负载的权限也可能间接获取命名空间中的秘密，要按实际能力审视权限。[Kubernetes Secret 最佳实践](https://kubernetes.io/docs/concepts/security/secrets-good-practices/)。

### 先看卡在哪个阶段

以下只读命令假设教学命名空间和 Deployment 已存在：

~~~bash
kubectl -n go-practice get pods -o wide
kubectl -n go-practice describe deployment inspection-api
kubectl -n go-practice get events --sort-by=.metadata.creationTimestamp
kubectl -n go-practice get services,endpointslices
kubectl -n go-practice logs deployment/inspection-api --all-containers=true --tail=100
~~~

Deployment 日志可能只选到部分 Pod，要结合具体 Pod 名、实例与时间继续查。容器重启后，针对该 Pod 使用 logs --previous 查看上一实例输出。kubectl top 需要指标服务，命令不可用不证明资源正常。

| 现象 | 先看证据 | 常见方向 |
|---|---|---|
| Pending | Events、调度原因、PVC | 资源不足、约束、卷未绑定 |
| ImagePullBackOff | 镜像事件、地址、身份 | 镜像不存在、权限、网络、架构 |
| CrashLoopBackOff | 当前/前次日志、退出原因 | 配置、崩溃、启动命令 |
| OOMKilled | 终止原因、内存趋势 | 上限、泄漏、大并发 |
| Running 但不 Ready | 探针、端口、依赖 | 路径错、启动慢、未就绪 |
| Service 无流量 | selector、EndpointSlice、端口 | 标签、targetPort、网络策略 |
| 外部 502 | 入口日志、Service、Pod | 路由、协议、后端与超时 |

先 Pod 内请求，再 Service，再入口，逐层定位。DNS 能解析不证明目标可达；TCP 通不证明 HTTP 或业务成功，[第 5 题讲义](../05-http-client/知识串讲.md)的同一种方法。

### 扩容之前找共享瓶颈

HPA 根据可用指标调整副本，需要指标链路和正确资源设定。CPU 低而队列积压，可能需要根据队列年龄等业务指标伸缩。更多 Worker 可能压垮数据库或触发模型限额，必须限制共享依赖预算。

PDB 约束部分自愿中断，不防止任意故障；副本跨节点分布、容量余量、节点维护、存储可用性要单独考虑。滚动发布另有可用性参数，不因有 PDB 就忽略发布过程。

数据库、消息系统放进 Kubernetes 之后，备份、磁盘、复制、权限与版本升级仍需维护。初学先把无状态 API 搬进去，再学习有状态运维。


## 把例子接回现有项目

只在教学环境把一个版本的 readiness 路径改错，保持应用本身正常；通过 Events、Pod状态、日志、EndpointSlice和直接请求确认原因。修复配置后验证流量恢复。资源/HPA/PDB先在讲义梳理，本题不把所有集群故障一次实现。

### 输入如何走到结果

API直连200，Service没有该Pod可用后端；探针路径修正后恢复。

### 分步动手

1. 先记录健康版本的Pod与EndpointSlice。
2. 只改探针路径，依次检查事件、直连和Service。
3. 恢复正确配置，验证任务闭环而非只看Ready绿色。

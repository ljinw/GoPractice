## 标准库逐步读：请求正文如何读、如何解码、如何报错

本题只预览资料，不保存。你要分清三层：HTTP请求正文提供字节；JSON解码把字节填入变量；业务校验决定这些值是否允许使用。任何一层成功都不自动证明下一层成功。

### Body是读取入口，不是已经解析的对象

r.Body的类型是io.ReadCloser，至少具备Read和Close。读取会消费流中的字节，不能假定第二次读取自动从头开始。普通服务端请求Body由HTTP服务器负责关闭；第05题客户端拿到的resp.Body则由客户端调用方关闭，这是不同的资源归属。

可以把Body直接交给json.Decoder，因为它需要io.Reader。接口的连接点是读取能力，Decoder不要求输入必须来自HTTP；也可以读strings.Reader、文件等。

### 解码相关签名怎样读

~~~go
func NewDecoder(r io.Reader) *Decoder
func (dec *Decoder) Decode(v any) error
~~~

NewDecoder的r是它自己的参数名，不是强制要求传入HTTP Request。json.NewDecoder(r.Body)创建一个读取Body的解码器；此时尚未保证JSON合法。Decode(&device)才尝试读取一份JSON并填入目标，返回一个error。

虽然Decode参数类型是any，运行时通常要求非nil的可写指针。传device和传&device不是同一件事：前者是值，后者让库有机会更新调用者持有的变量。Decode签名不承诺返回设备对象，设备内容通过参数目标被改变。

错误要先检查：空输入常得到io.EOF，坏JSON可能得到语法错误，类型不符也可能失败。err == nil仍可能得到一个Name为空的对象，因此还要业务校验。

### 完整小实验：解码不必先开服务器

保存为本题warmup/decode/main.go，运行go run ./warmup/decode/main.go。

~~~go
package main

import (
    "encoding/json"
    "fmt"
    "strings"
)

type Input struct {
    Name string `json:"name"`
}

// main用相同解码步骤比较正常、缺失、null和坏输入。
func main() {
    inputs := []string{
        `{"name":" sw-core "}`,
        `{}`,
        `null`,
        `{"name":123}`,
        `{`,
        "",
    }

    for _, text := range inputs {
        var input Input
        decoder := json.NewDecoder(strings.NewReader(text))
        err := decoder.Decode(&input)

        if err != nil {
            fmt.Printf("输入=%q，解码失败=%v\n", text, err)
            continue
        }

        input.Name = strings.TrimSpace(input.Name)
        fmt.Printf("输入=%q，name=%q，必填通过=%t\n",
            text, input.Name, input.Name != "")
    }
}
~~~

strings.NewReader(text)提供一个从字符串读取的Reader；for每轮创建新的Input和Decoder，避免把上一轮的值误带到下一轮。continue只跳到下一次循环；return会结束整个main，不是同一件事。

注意顶层null可能解码成功，但Name仍为空。本题Name必填，所以后续校验会拒绝它。不能把“JSON语法正确”当作“输入满足业务”。

### 本题错误为什么不能直接照搬http.Error

README要求失败正文为{"error":"invalid request"}。http.Error写的是纯文本，直接使用会改变合同。可在错误分支设置application/json，WriteHeader(400)，再用编码器写一个简单错误对象，并检查编码/写入错误。这份错误对象也要遵守响应提交顺序；处理完错误要return。

成功分支整理name后返回相同结构的JSON，IP格式验证安排在07题。不要一边解释API，一边悄悄把当前题增加成复杂资产录入系统。

### 请求大小、未知字段与多份JSON：第二轮扩展

~~~go
func MaxBytesReader(w ResponseWriter, r io.ReadCloser, n int64) io.ReadCloser
~~~

http.MaxBytesReader(w, r.Body, limit)返回一个有总读取限制的包装Body，不在创建时直接返回error。超过限制的错误出现在后续读取/Decode中。该方法适合HTTP入口的正文限制；超限如何映射状态要明确约定。

Decoder.DisallowUnknownFields()可要求拒绝无法映射的字段。Decode一次只读取下一份JSON，不保证后面没有第二份JSON或其他内容；严格只允许一份时需要继续读取并确认EOF。这些是后续明确的加练规则，当前README的验收保持原样。

### 变式与源码问题

对正常、空Body、坏JSON、null、空对象、空白Name、数字Name逐项预测：能否解码、字段是什么、业务是否通过、应回复什么。将&input误写成input，观察真正的错误，再修复。不要把所有失败都理解成指针错误。

源码先查Decode的目标校验与返回error路径，不要求通读整个扫描器。C#对照Deserialize和DTO时分别核对null、异常与必填规则；编译器的类型声明不能代替输入校验。

## 与本题相连的原理和工程做法

### 指针、方法、接口：分三次理解

`&device` 取得指向变量的指针；类型中的 `*Device` 表示指针类型；表达式中的 `*p` 取得它指向的值。Go 的参数仍然按值传递，传指针也是复制指针值；多个指针可以指向同一对象。

方法是在函数名前多写一个接收者，例如 `func (d *Device) Rename(name string)`。d 是本次方法调用使用的对象。`d.Rename("new")` 把这个对象与显式参数一起交给方法。指针接收者常用于修改对象或避免复制较大的对象，但它不自动保证并发安全。

接口描述“需要哪些方法”。只要某个类型的方法集合满足接口，它就实现该接口，不需要 implements 关键字。先认识 io.Writer、http.Handler 等真实用法，等需要替换数据库实现或假模型时再定义自己的小接口。

这些语法的准确规则可查 [Go 语言规范](https://go.dev/ref/spec)，命名、方法和错误处理习惯可对照 [Effective Go](https://go.dev/doc/effective_go)。

### 本题的HTTP合同与数据流

本题约定 POST /device-preview 接收设备JSON，整理name后返回预览；成功200，空正文、坏JSON、null或必填name无效返回400。预览不保存数据库。本题完整字段要求以README为准。

r.Body提供请求字节，Decoder.Decode把它们写进目标变量，因此要传入可写目标的指针。解码成功不代表业务有效：JSON null可能不触发语法错误，空对象也可能只是留下字段零值；还要显式检查本题必填字段。整理与校验之后才能编码回复。

先练清“读取失败”和“字段不合法”两种分支。请求体大小、未知字段和只允许一份JSON可作为后续加练的明确合同；先写预期，再实现，不能让示例的额外规则悄悄改变本题验收。

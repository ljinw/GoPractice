## 本题在项目中的位置

两项维护操作碰到同一组设备，锁冲突不能造成半批设备更新或无限重试。

本题只推进这个结果：把可重试的数据库死锁恢复限制在整个业务事务内。

## 先复习已经用过的写法

复习 for、error、defer 和 context；重复时处理的是整个事务，不是随便重跑最后一条 SQL。

## 这次新增的知识

锁等待与死锁不同；失败的事务边界决定什么需要回滚和重放。

## 带着项目问题读原理

### “锁”这个词下面有不同层次

| 名称 | 作用与例子 | 不应混淆 |
|---|---|---|
| 共享锁 S | 允许兼容的共享访问，阻止冲突修改 | 普通快照 SELECT 不一定加这种锁 |
| 排他锁 X | 保护修改，排斥冲突锁 | 不代表整张表都锁住 |
| 行/记录锁 | 保护命中的记录或索引记录 | SQL 扫描范围影响锁范围 |
| 表锁 | 保护表级操作或访问 | 与行锁粒度不同 |
| 意向锁 | 表示事务将申请更细粒度锁，便于协调 | 不是把所有行全锁住 |
| 间隙锁 | InnoDB 中约束索引记录之间的插入 | 条件与隔离级别相关 |
| Next-key 锁 | InnoDB 记录锁与前方间隙组合 | 不可直接套到 PostgreSQL |
| 元数据锁 MDL | 协调访问与表结构变化 | 可能使 ALTER 等待长事务 |
| 乐观锁 | 用 version 条件检测冲突 | 是应用策略，不是没有数据库锁 |
| 悲观锁 | 修改前先锁定将使用的记录 | 事务越长，阻塞风险越大 |
| 建议锁 | 应用约定的资源协调，如 PostgreSQL advisory lock | 未遵守约定的代码不受保护 |
| Go Mutex | 单进程内保护共享内存 | 不能保护其他服务实例 |

InnoDB 的锁通常与索引记录及范围相关；不要只看 WHERE 写得像“某一行”，就断言只锁一行。是否使用合适索引、是否唯一查找、是否范围扫描都重要。[InnoDB 锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)。PostgreSQL 另有表级、行级和 advisory 锁语义，应查它自己的合同。[PostgreSQL 显式锁](https://www.postgresql.org/docs/current/explicit-locking.html)。

### 两个窗口亲眼看到锁等待

以下只在 MySQL 8.4/InnoDB 的临时教学库中执行。先创建 lock_demo(id INT PRIMARY KEY, value INT NOT NULL)，插入 (1,0)、(2,0)。两个连接各自开启事务，不能在同一个连接里假装并发。

窗口 A：

~~~sql
START TRANSACTION;
SELECT value FROM lock_demo WHERE id = 1 FOR UPDATE;
-- 暂停在这里，尚未提交。
~~~

窗口 B：

~~~sql
START TRANSACTION;
UPDATE lock_demo SET value = value + 1 WHERE id = 1;
-- 观察等待；不要立即反复提交更多请求。
~~~

A 执行 COMMIT 后，观察 B 是否继续；然后 B COMMIT，读取最终值。接着另开实验：A 锁 1，B 锁 2，A 再要 2，B 再要 1，构造循环等待。InnoDB 通常检测死锁并回滚一个受害事务；应用必须正确处理失败。[InnoDB 死锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks.html)。

死锁恢复是重新执行整个可重试事务，并设置次数、退避和截止时间。已发短信、已调外部设备等副作用不能跟着无条件重放。降低死锁概率的方法包括一致的加锁顺序、缩短事务、合适索引、减少持锁期间的远程调用。

乐观更新示意：

~~~sql
UPDATE devices
SET name = ?, version = version + 1
WHERE tenant_id = ? AND id = ? AND version = ?;
~~~

检查 RowsAffected：1 表示本次基于预期版本更新成功；0 表示没有匹配，需要按业务处理冲突/不存在。使用乐观锁并不保证低冲突场景以外也高效，热点行频繁重试仍可能过载。

SQLite 是另一种并发模型。WAL 能改善读写并发，但仍只有一个写者，并非开启后就拥有 MySQL 那样的行锁；此处 SELECT FOR UPDATE 实验不能直接搬过去。[SQLite WAL](https://www.sqlite.org/wal.html)。


### 数据库报警后先区分四种拥堵

连接多：先看是正常并发、连接泄漏、池上限过大，还是慢事务让连接一直占用。  
SQL 慢：看具体语句、参数、计划和存储 I/O，不先全局改参数。  
锁等待：找阻塞链及最早持锁事务，区分“它运行久”与“它等待久”。  
容量增长：看表、索引、事务日志、临时文件、备份各占多少。

长事务可能来自应用拿着事务去等待远程 HTTP；数据库看起来没有大查询，却迟迟不能释放锁或清理版本。解决时要回到业务事务边界，而不是长期靠杀连接维持。

先记录问题证据再做操作。终止阻塞连接可能引发长回滚，影响并不会立刻消失。学习实验可以可控地停止自己的测试事务，生产动作需要明确影响与恢复方案。

## 把例子接回现有项目

用两台假设备与两个连接按相反顺序更新，复现死锁。正常业务按固定设备 ID 顺序加锁，死锁时回滚并有限重试完整事务，保留总截止时间。事务内不调用设备、通知或模型；非死锁错误不盲目重试。

### 输入如何走到结果

A 更新设备1→2，B 更新设备2→1；一个事务被选作受害者，完整重试后数据符合批次规则。

### 分步动手

1. 只在独立测试库建立两条设备记录，先固定双连接时序。
2. 读取驱动的稳定错误分类，写出重试与不可重试分支。
3. 恢复统一加锁顺序，再跑正常、死锁、超时三种路径。

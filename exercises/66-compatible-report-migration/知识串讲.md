## 本题在项目中的位置

灰度期间新旧API和Worker可能同时读写报告。

本题只推进这个结果：完成一次可回退的兼容字段演进。

## 先复习已经用过的写法

复习nil、零值、结构体标签和schema_version；新增字段要说明缺失时含义。

## 这次新增的知识

扩展—迁移—收缩分阶段；应用回退不等于数据库结构倒退。

## 带着项目问题读原理

### 新旧版本会同时运行

滚动期间新旧 API 都可能接收流量，Worker 也会消费不同时间的消息。新增字段考虑旧读者，删除字段等旧写者与读者退出；旧客户端也可能继续存在。

扩展—迁移—收缩：先新增兼容字段→应用兼容新旧→回填并校验→切换权威读取→确认旧版退出→最后删除旧字段。回填要分批、可重入、限速、能检查进度，避免锁住大表。

迁移由受控入口执行，不让每个 Pod 启动时同时抢着改结构。迁移失败阻止不兼容应用继续启动；在线 DDL 能力与影响按数据库版本和具体语句验证，“在线”不等于完全无阻塞。


### 五种状态都要检查

| 对象 | 常见回退动作 | 不能假定 |
|---|---|---|
| 应用 | 旧镜像/二进制 | 旧版一定能读新版数据 |
| 配置 | 兼容配置与开关 | 旧凭据仍有效 |
| 数据结构 | 保留扩展，恢复兼容读取 | 回滚镜像自动回滚 DDL |
| 消息 | 兼容新事件或暂停重放 | 新消息自动消失 |
| 外部副作用 | 对账、补偿、人工处理 | 已发通知/收费可撤销 |

Deployment 回滚针对 Pod 模板版本，不自动恢复数据库、独立 ConfigMap 历史值或外部系统。使用版本化配置引用有助于对应应用版本。[Deployment 回滚](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#rolling-back-a-deployment)。

### ORM 不会替你决定数据库正确性

GORM 让结构体与查询更方便，但你仍要看生成的 SQL、WHERE、事务和受影响行数。传统 API 中用结构体 Updates 默认忽略零值；想把 enabled 改成 false，需明确选择字段或使用适合的 map 更新，而不能只看对象里 false 已赋值。[GORM 更新合同](https://gorm.io/docs/update.html)。

N+1 查询是查 20 份报告后再为每份报告单独查设备。可以批量查关联、预加载或按需求 JOIN，但 JOIN 也可能扩大行数，导致分页重复和计数错误。先决定页面要哪些字段，再选择查询策略。


## 把例子接回现有项目

为报告加入可选 summary_version，先扩展结构和兼容读取，再限速、可重入地回填。定义默认与缺失语义；在v1/v2交叉读写中验证。删除旧字段不属于本题实施，写清未来收缩条件。迁移由唯一受控入口执行并记录版本。

### 输入如何走到结果

旧报告无新字段仍可读；v2写入新字段后v1仍可查询原合同。

### 分步动手

1. 先写四种交叉组合的读取预期。
2. 扩展字段并运行兼容测试，再少量回填。
3. 中断后重跑，验证旧应用仍能查询并创建任务。

### 读完后检验是否理解

先口述本题输入、需要改变的模块、权威数据在哪里、失败怎样被发现，再去 [需求与验收](README.md) 实现。讲义配置和表名是示意，先核对已有项目再使用；一处知识卡住可以单独练小片段，业务验收仍以实际运行证据为准。

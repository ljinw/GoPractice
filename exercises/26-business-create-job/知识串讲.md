## 与本题相连的原理和工程做法

### HTTP 合同不只是 URL

创建任务接口至少要约定：方法、路径、身份、JSON 格式、输入限制、成功状态、错误结构、幂等规则。比如 POST /inspection-jobs 成功返回 202 和 job_id，表示已经接收任务，不表示巡检已经完成。查询任务再读取 queued/running/succeeded/failed 状态。

400 表示输入有问题；401 通常表示缺少或无效认证；403 表示身份已识别但无权限；404 可以用于资源不存在，也可按策略隐藏越权资源；409 可表达状态或幂等冲突；429 表示限流。具体业务要一致，不能把所有异常包装成 HTTP 200。

JSON 解码要限制请求体大小，决定是否拒绝未知字段，校验必填和数值范围。字段缺失与 false/0 的区别会在更新接口中反复出现，必要时用指针或显式可选字段。数据库对象也不应原样暴露：密码、内部错误、租户信息必须经过出口审查。

### 表不是装 JSON 的抽屉

设备表保存设备当前资料；任务表保存一次执行请求；报告表保存结果快照。它们的生命周期不同。报告不能查询时再临时拼接最新设备名，否则设备改名会改写历史解释。

主键给每行稳定标识；唯一约束防止重复业务键；外键维护关联；NOT NULL 和 CHECK 表达允许的数据范围。应用校验负责给友好提示，数据库约束负责在并发下守住底线。两者同时存在有意义。

以下为 MySQL 8.4/InnoDB 教学表，明确用于隔离数据库，时间统一写入 UTC：

~~~sql
CREATE TABLE reports (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    job_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    UNIQUE KEY uq_report_job (tenant_id, job_id)
) ENGINE=InnoDB;
~~~

这里的联合唯一约束允许不同租户各自使用相同 job_id，但同一租户不能重复产生同一任务报告。若你的 job_id 已全局唯一，也可以选择相应全局约束；必须与业务 ID 策略一致。

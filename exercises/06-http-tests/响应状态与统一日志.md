
# 响应状态与统一日志：为什么w上没有“错误码字段”

[06题讲义](知识串讲.md) · [01题请求/响应基础](../01-http-health/知识串讲.md#native-http) · [fmt与log](../01-http-health/fmt与log详解.md) · [第一阶段路线](../../第一阶段标准库学习路线.md)

这是01–06基础建立后的综合实验。先会读接口、结构体、方法、函数值及defer，再一段一段做。当前的自动404/405日志需要放在路由器外层；最终状态来自实际响应写入过程，不应猜r或w的某个字段。

## 1. 分清查询规则和观察实际结果

mux.Handler(r)可以查询是否匹配到登记规则，未匹配时pattern为空，但它不返回最终HTTP状态码。正常处理函数也可能返回400/503，因此只查pattern不能作为所有响应的最终状态日志。

标准ResponseWriter只有写方法，没有GetStatusCode。你可以自己包装它：继续把真实的写操作交给原w，同时在自己的结构体里记下这次选用的状态。

## 2. 新语法先说明

下面的statusWriter是我们自定义的结构体，不是标准库类型。匿名嵌入http.ResponseWriter使它能转交原对象已有方法；自己的WriteHeader/Write则补上记录动作。status是自己定义的字段，所以你可以读取它；这和在原来的w上写w.StatusCode完全不同。

指针接收者使修改保留在同一个statusWriter对象里。next是一个http.Handler参数；next.ServeHTTP真正调用下一层。http.HandlerFunc把符合签名的函数适配为Handler；函数中引用next是闭包的一种使用，这里它只保存要调用的下一层处理器。

## 3. 可测试的核心代码

保存为本题warmup/statuslog/logging.go，第二段测试保存在同目录logging_test.go。运行go test -v ./warmup/statuslog/logging.go ./warmup/statuslog/logging_test.go，不需要固定端口，也不改你的Demo.go。

~~~go
package main

import (
    "log"
    "net/http"
)

// statusWriter转发普通HTTP响应，同时记录最终状态；不缓存正文。
type statusWriter struct {
    http.ResponseWriter
    status int
}

// WriteHeader记录首次最终状态；信息响应继续交给底层，不占用最终状态。
func (w *statusWriter) WriteHeader(code int) {
    if code >= 100 && code < 200 {
        w.ResponseWriter.WriteHeader(code)
        return
    }
    if w.status != 0 {
        return
    }
    w.status = code
    w.ResponseWriter.WriteHeader(code)
}

// Write补齐隐式200，再转发正文；返回值保留底层字节数和error。
func (w *statusWriter) Write(data []byte) (int, error) {
    if w.status == 0 {
        w.WriteHeader(http.StatusOK)
    }
    return w.ResponseWriter.Write(data)
}

// withStatusLog只记录正常返回的普通请求；状态来自写入过程而非匹配猜测。
func withStatusLog(next http.Handler, logger *log.Logger) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        recorder := &statusWriter{ResponseWriter: w}
        next.ServeHTTP(recorder, r)

        status := recorder.status
        if status == 0 {
            status = http.StatusOK
        }
        logger.Printf("状态=%d，方法=%s，路径=%q", status, r.Method, r.URL.Path)
    })
}
~~~

0是我们记录“尚未显式确定最终状态”的初始值，不是HTTP状态码。第一次Write前补200；处理器正常返回且从未写任何内容，普通HTTP服务最终也采用200。返回后记录不能证明客户端完整接收，更不能代替传输错误与panic日志。

## 4. 用一个新路由实验，而不是覆盖旧需求

~~~go
package main

import (
    "bytes"
    "log"
    "net/http"
    "net/http/httptest"
    "strings"
    "testing"
)

// TestStatusLog检查成功、处理器报错与路由自动回复都能记录实际状态。
func TestStatusLog(t *testing.T) {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /ready", func(w http.ResponseWriter, r *http.Request) {
        http.Error(w, "暂时不可用", http.StatusServiceUnavailable)
    })

    var output bytes.Buffer
    handler := withStatusLog(mux, log.New(&output, "", 0))

    cases := []struct {
        method string
        path   string
        code   int
        text   string
    }{
        {"GET", "/ready", 503, "状态=503"},
        {"POST", "/ready", 405, "状态=405"},
        {"GET", "/missing", 404, "状态=404"},
    }
    for _, tc := range cases {
        output.Reset()
        writer := httptest.NewRecorder()
        handler.ServeHTTP(writer, httptest.NewRequest(tc.method, tc.path, nil))
        if writer.Code != tc.code {
            t.Errorf("响应=%d，期望=%d", writer.Code, tc.code)
        }
        if !strings.Contains(output.String(), tc.text) {
            t.Errorf("日志缺少%s：%q", tc.text, output.String())
        }
    }
}
~~~

测试通过后再加一个写正文但不WriteHeader的200路由、一个不写内容的200路由。自己补断言，再故意删掉Write里的补200，观察哪些用例能发现。若剩余fallback使日志仍对，不要假装测试失败；应增加直接观察包装器记录状态的检查，理解不同观察点。这是练可证伪，不是背一个“应该变红”的结论。

## 5. 怎样接到已有程序

在已有main登记完mux路由后：

~~~go
logger := log.New(log.Writer(), "", log.LstdFlags)
handler := withStatusLog(mux, logger)
~~~

然后将ListenAndServe第二个参数从mux换为handler。withStatusLog及statusWriter定义放在同一main包的文件里；只有main.go时也可以放在main函数外，但不能把type和方法定义写进main内部。多个源文件组成一个程序时使用模块并运行go run .，不要只运行一个遗漏依赖定义的文件。

请求顺序：客户端→日志包装器→mux→实际处理器或标准404/405→记录最终状态。日志里状态>=400可由你约定显示错误标记；标准log本身没有自动分级，本题先保留准确状态，不把所有404都当成程序崩溃。

## 6. 教学边界

这份包装器只用于普通请求/响应教学，未承诺保留Flusher、Hijacker等可选接口能力，也未涵盖SSE、WebSocket、panic恢复或HTTP协议升级；后续做这些功能前必须核对或采用合适的现有中间件。不要把教学包装直接宣布为生产通用实现。

日志可以记录自己观察的响应状态，写入error仍由实际处理器单独处理。没有保存正文，内存里不会自动多出完整响应副本。此实验先让你理解机制，后面换chi/Gin时比较框架如何提供相同能力。

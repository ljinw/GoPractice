## 带着项目问题读原理

### 文档灵活，但业务仍需要结构

关系数据库适合表达约束清晰的关联和事务。MongoDB 用 BSON 文档组织数据，适合把经常一起读取、结构可能变化的内容放在一起。报告章节、不同检查类型的事实载荷可以用它做建模实验；“能存 JSON”本身不是引入第二个数据库的充分理由。

~~~json
{
  "_id": "report-demo-001",
  "tenant_id": "tenant-a",
  "job_id": "job-001",
  "schema_version": 1,
  "summary": {"abnormal": 1, "missing": 0},
  "sections": [
    {"kind": "cpu", "fact_id": "fact-001", "value": 92, "unit": "%"}
  ]
}
~~~

这个例子让报告与有限章节一起读出。若把每次采样无限追加到同一个数组，文档会持续膨胀，更新和大小限制都会成为问题。要按查询方式决定嵌入还是引用，必要时拆集合与时间分桶。MongoDB 的灵活模型不代表不需要字段校验和版本。[MongoDB 数据建模](https://www.mongodb.com/docs/manual/data-modeling/)。

### 原子性与更新条件

单文档写入具有原子性；并发更新时可把预期 version 加入过滤条件以检测冲突。多文档一致性需要另外设计，支持事务也不意味着应该把所有操作塞进大事务。[MongoDB 原子性与事务](https://www.mongodb.com/docs/manual/core/write-operations-atomicity/)。

通用更新示意：对允许修改的设备元数据文档，用 _id、tenant_id、version 过滤，修改后 version 加 1，并检查 matched/modified 结果。读时状态不保证写时仍成立。本项目已完成报告是不可变快照，不采用原地修改；报告重复创建用唯一业务键和结果复用。

索引按查询建立，例如 tenant_id 与 created_at 的复合索引；使用 explain 观察扫描的文档数与返回数。聚合管道负责筛选、展开、分组、投影等处理，排序和分组也需要内存与 I/O。不要把复杂业务都隐藏进一条无法解释的管道。

### 运维上要看哪些区别

副本集用于可用性；write concern 决定写入确认要求，read concern/read preference 影响读取语义与位置。分片用于分布数据与负载，分片键选择会影响热点与路由，不能把“开启分片”当作通用性能按钮。

备份、恢复、权限、连接池、磁盘与索引增长仍需要管理。TTL 索引用于到期清理时，不应把后台清理的时间当成精确业务截止点；读取侧仍按过期规则判断。报告留存期限与审计数据要分开设计。

本课程对照实验先把报告正文单独存 MongoDB，设备与任务仍在关系库。跨库写入不会自动成为一个事务：可先生成不可变正文，再提交带状态的索引，用重试与对账处理失败；必须防止索引指向不存在的正文。不要在初学阶段无需求地把每种数据都分散到不同库。


### 一个列表接口为什么越来越慢

假设任务表增长到百万行，接口每次按租户筛选状态、按创建时间倒序，取最近 20 条。数据少时全表扫描也快，数据多后才暴露问题。优化必须记录数据量、分布、SQL、参数、并发、耗时与结果正确性。

连接池等待、锁等待、磁盘读、排序、网络传输、JSON 编码都可能贡献延迟。先分段测量，再看数据库执行计划，不要看到接口慢就加索引或加 Redis。

## 把例子接回现有项目

为现有 MongoDB 报告生成固定合成数据，查询带可信 tenant_id、排序与条数上限；比较建索引前后的 explain 文档扫描量、返回量和耗时。已有 schema_version 保持可识别，不使用无限增长数组存全部历史采样。

### 输入如何走到结果

租户A最近20份报告；索引前后结果和顺序一致。

### 分步动手

1. 先用与原接口一致的过滤和排序得到基线。
2. 只增加与该查询相关的索引，比较扫描/返回数量。
3. 复测空结果、大租户与小租户，记录没有改善的情况。

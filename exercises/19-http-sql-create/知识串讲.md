## 与本题相连的原理和工程做法

### 三层不是三个空文件夹

handler 负责 HTTP 输入输出；service 负责业务决定；repository 负责数据读写。创建巡检时，handler 解析设备编号，service 判断设备可用、用户有权、幂等键一致，repository 在事务中落地任务和发布事件。

层次的价值是让规则容易找到和测试。只有一个打印接口时不必预先建十几个空包。随着持久化、事务和假模型替换出现，再引入小接口。接口尽量贴近使用方需求，例如只需要 GetDevice 就不要求实现二十个数据库方法。

依赖一般在启动时组装，再交给处理器。不要每个请求重新建数据库连接池，也不要在多个包各创建一个隐藏全局模型客户端。构造失败就明确阻止启动，避免服务看起来已启动却第一次请求才发现核心配置缺失。

### 本题的HTTP合同与数据流

本题约定 POST /devices：校验并保存一台设备，成功201；输入无效400，IP唯一约束冲突409，其他存储错误500。响应结构与生成ID以README为准。HTTP受理和数据库持久化要通过一次真实的隔离实验连起来。

数据流是“请求JSON→输入校验→服务/仓储→参数化SQL→返回设备→HTTP响应”。请求的ctx沿数据库调用传下去；失败分支不要把数据库内部错误原文返回给客户端。错误分类看可信类型或驱动错误码，不能靠把所有错误都当作重复IP。

两个并发请求可能都通过写前查询，最终仍要由数据库唯一约束守住IP唯一性。提交成功后再查、重启后再查，才能证明数据真的保存。201不用于后续耗时任务受理；后台巡检的202合同会在第26题学习。

### 表不是装 JSON 的抽屉

设备表保存设备当前资料；任务表保存一次执行请求；报告表保存结果快照。它们的生命周期不同。报告不能查询时再临时拼接最新设备名，否则设备改名会改写历史解释。

主键给每行稳定标识；唯一约束防止重复业务键；外键维护关联；NOT NULL 和 CHECK 表达允许的数据范围。应用校验负责给友好提示，数据库约束负责在并发下守住底线。两者同时存在有意义。

以下为 MySQL 8.4/InnoDB 教学表，明确用于隔离数据库，时间统一写入 UTC：

~~~sql
CREATE TABLE reports (
    id BIGINT PRIMARY KEY,
    tenant_id BIGINT NOT NULL,
    job_id BIGINT NOT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME(6) NOT NULL,
    UNIQUE KEY uq_report_job (tenant_id, job_id)
) ENGINE=InnoDB;
~~~

这里的联合唯一约束允许不同租户各自使用相同 job_id，但同一租户不能重复产生同一任务报告。若你的 job_id 已全局唯一，也可以选择相应全局约束；必须与业务 ID 策略一致。

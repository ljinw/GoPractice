## 这题在完整业务中的位置

排障关联：把一次请求的编号带回用户，帮助后续追查。 [查看完整业务](../../业务主线.md)。

## 这次做成什么

用中间件统一设置响应头 X-Request-ID，回到我们最初读过的代码。

## 具体需求

从请求头取编号并去掉两端空白；合法规则为 1~128 位 ASCII 字母、数字或 ._:-。合法就沿用，否则用 crypto/rand 生成 16 字节并编码为十六进制。写响应头后再调用下一处理器。随机数生成失败则返回 500，不执行下一处理器。

## 输入与结果

```text
请求头 X-Request-ID: demo-001 → 响应同编号
缺失或不合法 → 响应为新生成的编号
```

## 怎样算完成

- [ ] 合法编号保留；空白、内部空格、129 字符编号被替换。
- [ ] 400、404、409 等响应仍有编号，后续处理器每次只执行一次。
- [ ] 通过可替换的生成函数模拟生成失败：500，业务处理器未执行；并发请求没有共享变量覆盖。

## 本题常用写法（遇到再看）

```go
rawID := r.Header.Get("X-Request-ID")
w.Header().Set("X-Request-ID", requestID)
```

- 【语法区别】r.Header 是字段；w.Header() 是方法调用。Get 返回字符串，Set 没有返回值。
- 【习惯】rawID 表示原始值，requestID 表示整理后的值；ID 缩写通常保持大写。
- 【协议选择】X-Request-ID 是常见的关联请求头，不是 HTTP 强制字段；它不能替代登录凭据。本题的字符规则由应用约定。
- 【中间件惯例】next 表示下一个处理器；`next.ServeHTTP(w, r)` 把请求继续传下去。响应头应在它之前设置。

本题允许编号生成失败，所以规范化函数可以返回 `(string, error)`：先判断错误再用字符串。原项目示例返回一个 string；调用时接几个值取决于各自真实签名。

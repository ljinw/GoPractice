## 与本题相连的原理和工程做法

### 先把原片段拆开

~~~go
func (h *httpHandler) answer(w http.ResponseWriter, r *http.Request) {
    requestID := normalizeRequestID(r.Header.Get("X-Request-ID"))
    w.Header().Set("X-Request-ID", requestID)
}
~~~

这里定义 answer 方法，接收者 h 的类型是 *httpHandler。httpHandler 是项目自定义类型，不是 Go 标准库强制要求的名字。h 可以保存服务、仓储、日志器等依赖；这三行没使用 h，并不代表所有 HTTP 处理器都必须带一个空接收者。

w、r 是两个参数名，分别常用于响应写入器与请求。类型和顺序匹配 net/http 处理函数合同，名称可以改。answer 的参数括号后没有返回类型，因此它没有 Go 返回值；HTTP 响应通过 w 产生。**Go 的 return 与浏览器收到响应，是两个不同层面的结果。**

注册时可以写 `mux.HandleFunc("GET /answer", h.answer)`。这里的 h.answer 是绑定了接收者的方法值，形状为 `func(http.ResponseWriter, *http.Request)`。路由器保存它；请求到来时，HTTP 服务准备 w、r 并调用。若写 h.answer(...)，则是当场执行调用，需要此刻提供参数。

### 从最内层向外读

把长表达式拆成相同效果的几步：

~~~go
// 示意：放在 answer 方法体内。
incomingHeaders := r.Header
rawID := incomingHeaders.Get("X-Request-ID")
requestID := normalizeRequestID(rawID)
outgoingHeaders := w.Header()
outgoingHeaders.Set("X-Request-ID", requestID)
~~~

| 表达式 | 输入来自哪里 | 结果是什么 |
|---|---|---|
| r.Header | 当前 HTTP 请求 | 请求头集合，是字段 |
| Get("X-Request-ID") | Header 集合与字段名 | 一个字符串；没有值时为空字符串 |
| normalizeRequestID(rawID) | 上一步字符串 | 取决于项目定义，这里假定返回字符串 |
| requestID := ... | normalize 的结果 | 新建局部变量，类型由右侧推断 |
| w.Header() | 响应写入器 | 可修改的响应头集合，是方法调用 |
| Set(name, value) | 头名称和值 | 修改响应头；本身没有返回值 |

这里最容易混的是 `r.Header` 没有括号，因为读取字段；`w.Header()` 有括号，因为调用方法。同样叫 Header，所在类型不同，定义也不同。

原片段没有 normalizeRequestID 的定义，因此不能断言它会去空格、生成 UUID 或校验字符。函数名只表达意图，实际行为必须查定义。教学里可以约定：接受限定长度的字母数字及少量分隔符，缺失或非法时生成新编号；生成失败应该有明确错误处理。这是业务合同，不是 HTTP 标准自动提供的能力。

### “设置了头”为什么还没发出去

通常先设置 Header，再调用 WriteHeader 或写正文。首次写正文而未显式发最终状态码时，net/http 通常隐式发送 200。最终响应头发出之后，再修改普通头字段通常不能改变已经发出的内容。因此 Request ID 应在写正文前设置。请求 r 表示收到什么，w 负责发回什么；改请求头并不等于改响应头。[net/http 的 ResponseWriter 与 Header 合同](https://pkg.go.dev/net/http#ResponseWriter)。

X-Request-ID 常用于关联入口请求和日志，不是登录凭证，也不是幂等凭证。外部传入的值要限制长度和字符，不能直接信任其唯一性。多服务追踪还会涉及 Trace ID；一个用户创建的异步任务则有独立 job_id。这些编号有关联，但职责不同。

### 中间件为什么能包住处理器

~~~go
// 示意：这是最小形状，next 表示下一个处理器。
func Wrap(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 进入业务前的检查放这里。
        next.ServeHTTP(w, r)
        // 业务返回后的统计放这里。
    })
}
~~~

从外到内读：Wrap 收到一个满足 http.Handler 的值，返回另一个 Handler。内部匿名函数捕获 next，这叫闭包。`http.HandlerFunc(...)` 是把函数转换成一个具有 ServeHTTP 方法的适配类型，所以它能放到 Handler 接口位置。

若调用关系是 A(B(C(handler)))，进入顺序为 A→B→C→业务，返回顺序相反。认证失败直接写出错误并 return，就不会进入下一层。调用 next 两次则可能执行两次业务，这属于严重副作用问题。

Request ID 要在日志需要它之前准备好；认证后才知道可信的用户身份；业务授权又需要资源所属者。panic recovery 与日志包裹顺序会影响能否记录最终错误。没有一套顺序适合所有项目，先写出每层依赖什么，再确定顺序。

### 常用中间件不等于可以随意拼装

| 能力 | 为什么需要 | 最容易忽略的边界 |
|---|---|---|
| Request ID | 对齐请求和日志 | 外部值校验，不能代替身份 |
| 认证 | 确认调用方 | token 过期、签名、撤销策略 |
| 授权 | 判断可访问的对象和动作 | 只验证登录仍可能越权 |
| 限流 | 防止过载 | 单机计数不等于全局限额 |
| recovery | 将部分 panic 转为受控失败 | 不应吞掉证据；不能逆转已提交事务 |
| 访问日志 | 记录耗时与最终结果 | 写过响应后不能再伪造成功或失败码 |
| CORS | 控制浏览器跨源读取 | 不是身份认证或服务端访问控制 |
| 超时 | 限制请求成本 | 下游必须配合；长连接另设策略 |

包装 ResponseWriter 统计状态码时，还要保留需要的流式等能力，否则 SSE 可能失效。先用成熟实现并理解合同，再按需自写最小版本。

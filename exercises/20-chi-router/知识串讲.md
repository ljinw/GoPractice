## 与本题相连的原理和工程做法

### 先判断它替你省了哪一层工作

| 工具 | 接管什么 | 仍需你决定 | 什么时候学 |
|---|---|---|---|
| net/http | HTTP 服务与客户端基础合同 | 路由、业务、权限、存储 | 最先 |
| chi | 兼容标准 Handler 的路由组合 | 领域规则、数据库与部署 | 能写标准处理器后 |
| Gin | 路由、Context、绑定、响应辅助 | 输入语义、授权、错误分类 | 对照同一接口 |
| database/sql | 数据库通用访问与连接池 | 驱动、SQL、事务、约束 | 接口能接收数据后 |
| GORM | ORM 映射与查询构造 | SQL 性能、事务、零值语义 | 能读 SQL 后 |
| Kratos | 服务合同与传输、生命周期等组织 | 服务边界、数据一致性 | 单体业务跑通后 |
| Eino | 模型组件与 AI 流程编排 | 证据、授权、质量和成本 | 事实报告稳定后 |

chi 延续标准库处理器形状；Gin 的处理函数通常接收 *gin.Context。Gin Context 与标准 context.Context 不是同一个概念，调用数据库、RPC 时仍要管理请求取消和截止时间。框架上下文也不能随意留给请求结束后的 goroutine 使用。[chi 官方说明](https://github.com/go-chi/chi)、[Gin 官方文档](https://gin-gonic.com/en/docs/)。

学习时把同一个“按 ID 查询设备”接口分别用 net/http、chi、Gin 表达；对照输入、服务调用、输出，观察框架改变了什么。最终业务只保留选定的一套入口。更换路由框架不应让“谁能访问设备”的规则出现三份。

### 中间件为什么能包住处理器

~~~go
// 示意：这是最小形状，next 表示下一个处理器。
func Wrap(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 进入业务前的检查放这里。
        next.ServeHTTP(w, r)
        // 业务返回后的统计放这里。
    })
}
~~~

从外到内读：Wrap 收到一个满足 http.Handler 的值，返回另一个 Handler。内部匿名函数捕获 next，这叫闭包。`http.HandlerFunc(...)` 是把函数转换成一个具有 ServeHTTP 方法的适配类型，所以它能放到 Handler 接口位置。

若调用关系是 A(B(C(handler)))，进入顺序为 A→B→C→业务，返回顺序相反。认证失败直接写出错误并 return，就不会进入下一层。调用 next 两次则可能执行两次业务，这属于严重副作用问题。

Request ID 要在日志需要它之前准备好；认证后才知道可信的用户身份；业务授权又需要资源所属者。panic recovery 与日志包裹顺序会影响能否记录最终错误。没有一套顺序适合所有项目，先写出每层依赖什么，再确定顺序。

## 标准库逐步读：地址字符串、连接对象和超时

这次第一次主动建立TCP连接。目标限定一个已知本机端口；IP解析、端口范围校验、连接建立和业务请求是不同步骤。

### 地址怎样组成，为什么不用随手拼冒号

~~~go
func JoinHostPort(host, port string) string
func DialTimeout(network, address string, timeout time.Duration) (Conn, error)
~~~

net.JoinHostPort接收主机和端口文本，返回地址字符串；不返回error、不连接、不保证端口满足业务范围。它会处理IPv6需要的方括号等形式；本题仍只用127.0.0.1。整数端口可用strconv.Itoa转为文本。

DialTimeout的network在这里是"tcp"，不是设备名；address是"127.0.0.1:18080"这类目标，timeout是持续时间，不是绝对时间点。它返回Conn接口与error；先检查error，成功后才使用并负责关闭连接。

net.Conn提供Read、Write、Close、LocalAddr、RemoteAddr、SetDeadline等方法。它不是已经解析好的HTTP响应，里面没有StatusCode。可以把连接作为io.Reader/io.Writer使用，但TCP层不负责理解GET、JSON或状态码。

### 超时只约束了哪一段

DialTimeout限制连接建立（及相关解析）这一阶段，不会自动给连接之后的所有Read/Write都设期限。后续读写要设置Deadline，或使用具有各自总预算的更高层客户端。

连接成功只说明此刻TCP握手成功；不证明认证通过、数据正确或HTTP接口健康。连接失败也要保留实际原因，不把连接拒绝、超时和非法端口都简单叫“设备离线”。

### 完整小实验：只连一次，结束后释放

保存为本题warmup/dial/main.go，先启动自己的01题服务，再运行go run ./warmup/dial/main.go。

~~~go
package main

import (
    "fmt"
    "log"
    "net"
    "strconv"
    "time"
)

// probe仅诊断一个本机端口；无效端口不进入网络调用。
func probe(port int) error {
    if port < 1 || port > 65535 {
        return fmt.Errorf("端口超出范围: %d", port)
    }

    address := net.JoinHostPort("127.0.0.1", strconv.Itoa(port))
    conn, err := net.DialTimeout("tcp", address, time.Second)
    if err != nil {
        return fmt.Errorf("连接本机端口%s失败: %w", address, err)
    }
    if err := conn.Close(); err != nil {
        return fmt.Errorf("关闭本机连接失败: %w", err)
    }
    return nil
}

// main在最外层展示结果，不把同一错误每层重复打印。
func main() {
    if err := probe(18080); err != nil {
        log.Print(err)
        return
    }
    fmt.Println("connected")
}
~~~

probe返回一个error，没有额外bool；nil表示本次连接及关闭步骤完成。外层根据err决定是否打印connected。连接建立后立即Close，所以这段没有等待HTTP响应；不要用它声称完成了/health业务。

Close也是可能失败的方法，不是每个库调用都可以忽略结果。若把连接保留给后续读写，可在拥有连接的函数里安排defer清理，并明确写错误和清理错误的优先级。

### Dialer与context是下一轮对照

net.Dialer可以配置Timeout等选项，DialContext(ctx, "tcp", address)把建立连接的取消预算接入context；它成功返回连接后，原ctx不自动为连接后续所有读写提供持续取消。不要从函数名包含Context推断整条业务都被自动管理。

本题先把DialTimeout练稳，再对照Dialer。HTTP Client内部也会建TCP连接，但通常不需要你为每个HTTP请求手工Dial；高低层API各有资源拥有者。

### 变式与源码问题

分别准备启动服务、停止服务、非法端口0/-1/70000，写预期和实际错误。循环20次只连接这个已知本机服务，每次都Close，不改成端口扫描。超时通常是上限，连接被拒绝可能立即失败，不要求每次恰好等1秒。

想测试真正的超时，应使用受控替身或隔离实验；随便选一个地址可能立即失败，也可能经过真实网络。源码先看DialTimeout怎样构造Dialer，查成功返回后谁拥有Conn；C#对照TcpClient时同样要分开连接与读写期限。

## 与本题相连的原理和工程做法

### 一次请求经过哪些边界

客户端先解析主机名，建立 TCP 连接；HTTPS 还要进行 TLS 握手和证书验证，之后发送 HTTP 请求。Nginx 可以终止 TLS，再与后端建立另一条连接。Go 服务按方法和路径选择处理器，读取请求、调用业务、写出状态码、响应头和正文。

因此“端口能连上”只说明连接层某一步成功，不说明 HTTP 路径存在、认证正确或 SQL 能执行。`connection refused`、连接超时、TLS 证书错误、HTTP 404、HTTP 500 是不同阶段的证据。排障时先把失败定位到阶段，再决定看哪一层。

TCP 提供字节流，没有“每次 Write 对应一次 Read”的消息边界。自定义协议要约定换行、长度前缀或其他 framing；读取需要限制最大长度，处理半包、粘包和对端关闭。网络课中的 echo 可以用换行分隔，再通过故意分两次写入一行来验证理解。

### 超时是一份总预算

假设入口允许 3 秒，认证已花 100 毫秒，SQL 花 500 毫秒，下游 RPC 不应又独立等待 30 秒。将请求 ctx 向下传，再按步骤设置更短预算。预算数值来自业务目标和测量，文中的数字只是教学例子。

客户端复用 http.Client/Transport；成功获得响应后要关闭 Body，是否继续读完取决于响应大小和复用需求。服务端要明确读取请求头、空闲连接、写响应等超时；流式 SSE 与普通短请求需要不同策略，不能照搬一个短写超时。

客户端取消后，普通查询通常也应取消；已经可靠接收的后台任务应由持久化任务系统管理生命周期，不能简单挂在已经结束的请求 ctx 上。两者通过 job_id 关联，而不是依靠一个永不返回的 HTTP 请求。

### 你应形成的排障习惯

先记请求发生时间、版本、请求编号、具体路径与状态，再判断失败层。localhost 在宿主机、容器、Pod 内分别指向各自网络空间；Go 只监听 127.0.0.1 时，容器外经端口映射也可能访问不到。进入容器部署阶段再按网络隔离设计选择监听地址。

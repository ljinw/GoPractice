## 与本题相连的原理和工程做法

### 认证、授权、审计是三件事

认证回答“你是谁”；授权回答“这个资源你能不能读或改”；审计回答“谁在什么时候对什么做了什么，结果怎样”。读取 /inspection-jobs/123/report 时只检查 token 合法还不够，还要检查 report 属于当前用户或租户。

租户不能由客户端随意填一个请求头就变可信。资源查询带上可信租户范围，缓存 Key 和消息任务也要保持范围；AI 检索同样受限。服务之间的身份与终端用户身份要区分，不能让“内部服务已认证”自动变成读取任何用户数据的权限。

日志中的 user_id、tenant_id 是审计线索，不是证明访问获准的机制。敏感正文、密码、token 不应进入普通日志；审计记录要有访问控制和保留策略。

### 常用中间件不等于可以随意拼装

| 能力 | 为什么需要 | 最容易忽略的边界 |
|---|---|---|
| Request ID | 对齐请求和日志 | 外部值校验，不能代替身份 |
| 认证 | 确认调用方 | token 过期、签名、撤销策略 |
| 授权 | 判断可访问的对象和动作 | 只验证登录仍可能越权 |
| 限流 | 防止过载 | 单机计数不等于全局限额 |
| recovery | 将部分 panic 转为受控失败 | 不应吞掉证据；不能逆转已提交事务 |
| 访问日志 | 记录耗时与最终结果 | 写过响应后不能再伪造成功或失败码 |
| CORS | 控制浏览器跨源读取 | 不是身份认证或服务端访问控制 |
| 超时 | 限制请求成本 | 下游必须配合；长连接另设策略 |

包装 ResponseWriter 统计状态码时，还要保留需要的流式等能力，否则 SSE 可能失效。先用成熟实现并理解合同，再按需自写最小版本。

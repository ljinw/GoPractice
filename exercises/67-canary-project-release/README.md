## 业务为什么需要它

新版可能在真实调用链下出错，需要小范围验证并及时停止放量。

## 这次做成什么

执行一次有明确判定条件的灰度。

## 具体需求

在本地教学入口按可信假账号稳定分组到v1/v2，记录新旧版本业务与资源指标；定义最小样本、观察时间、错误/越权/重复副作用的停止条件。使用支持对应路由能力的组件；不能把Pod数量比例直接当精确请求比例。所有通知与模型保持fake。

## 输入与结果

教学账号A固定v2、B固定v1；v2故意错误达到条件→停止继续放量。

## 今天从这里动手

1. 先确定两个明确版本与可信分组方式。
2. 跑正常负载满足样本，再只对新版注入延迟或失败。
3. 形成放量/暂停结论，保留指标与业务结果证据。

## 怎样算完成

- [ ] 同账号路由稳定，客户端随意伪造灰度标识不能改变授权范围。
- [ ] 注入新版故障后按预先条件停止，不以少量健康检查放行。
- [ ] 数据库、队列和Worker也在兼容范围，记录已进入新版的任务。

## 实验记录与边界

在本题目录记录实际环境版本、输入、预期、结果和证据路径；未运行的检查保持未勾选。只使用隔离教学数据、本机/本地教学服务、假通知和假模型。真实生产上线、真实设备及付费调用不在本题授权内。

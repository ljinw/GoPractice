## 标准库逐步读：HTTP正文怎样成为JSON

本题配套encoding/json，是为了把数据以约定格式放进HTTP响应；仍需先理解[ResponseWriter与状态码](../01-http-health/知识串讲.md#native-http)。Content-Type声明格式，编码器负责生成字节，两者不会互相替代。

### 先认类型、字段与标签

~~~go
type Device struct {
    Name string `json:"name"`
    IP   string `json:"ip"`
}
~~~

这是类型定义，放在函数外。Device是自己定义的类型名；Name/IP是导出字段；name/ip是对外JSON字段名。反引号括起来的是结构体标签字符串，json键由编码库识别。字段未导出时，给它加标签也不能使标准编码器随意读写。

device := Device{Name: "sw-core", IP: "192.0.2.10"}创建一个值，字段里的IP此时只是文本；编码不连接设备，也不验证设备在线。

### 两条编码路线的签名与用途

~~~go
func Marshal(v any) ([]byte, error)
func NewEncoder(w io.Writer) *Encoder
func (enc *Encoder) Encode(v any) error
~~~

这些签名属于encoding/json包，调用加json.。Marshal接收一个值，返回JSON字节切片及error；它只生成字节，暂时没有发送HTTP。NewEncoder接收一个能写字节的目标，返回编码器指针；它不立即完成编码，也不返回第二个error。Encode是编码器的方法，真正把值编码并写入目标，只返回一个error。

json.NewEncoder(w).Encode(device)可以拆为encoder := json.NewEncoder(w)，再err := encoder.Encode(device)。Encode的正常输出末尾会追加换行。json.Marshal不自动追加这个换行。

| 需求 | 用法 | 错误在哪检查 |
|---|---|---|
| 先得到JSON字节，例如还要计算长度/保存 | json.Marshal | Marshal返回的err |
| 向一个Writer直接编码 | json.NewEncoder(...).Encode | Encode返回的err |
| HTTP响应声明JSON | w.Header().Set | 此处无返回值，必须在响应提交前设置 |
| 写普通Go调试输出 | fmt.Printf("%+v", device) | 这是调试格式，不保证是JSON |

### 完整小实验：先把编码结果写进内存

保存为本题warmup/json/main.go，运行go run ./warmup/json/main.go。

~~~go
package main

import (
    "bytes"
    "encoding/json"
    "fmt"
    "log"
)

type Device struct {
    Name string `json:"name"`
    IP   string `json:"ip"`
}

// main比较先生成JSON字节与直接编码到Writer的结果。
func main() {
    device := Device{Name: "sw-core", IP: "192.0.2.10"}

    data, err := json.Marshal(device)
    if err != nil {
        log.Print(err)
        return
    }

    var buffer bytes.Buffer
    encoder := json.NewEncoder(&buffer)
    if err := encoder.Encode(device); err != nil {
        log.Print(err)
        return
    }

    fmt.Printf("Marshal=%q\n", string(data))
    fmt.Printf("Encode=%q\n", buffer.String())
}
~~~

两份数据都可解析为同一设备，Encode多一个末尾换行。再把Name改成未导出name，并同步修改创建值的位置，观察字段消失；然后恢复。标签改变的是外部名字，不是是否导出的规则。

### 在已有HTTP处理函数里怎样安排

先准备要输出的数据，设置Content-Type，再编码。对于本题结构固定的Device，可以直接Encode到w并检查error。默认200如何产生，回到01题的Write/WriteHeader顺序实验。

若值可能包含JSON不支持的类型，例如channel，Marshal/Encode可能报错。需要在发送状态/正文前知道编码是否成功时，先Marshal，成功后再设置头/状态并写字节。写出一部分响应后才报错时，不能再追加另一份500 JSON装作已经替换原响应；记录错误并按响应生命周期处理。

本题默认不要求你设计通用响应库；先读懂一次编码及写入。不要忽略err，也不要在没有验证的前提下把库对象所有字段原样暴露给客户端。

### 小实验、测试与源码问题

给样例增加Enabled bool字段，在独立变式里观察false怎样编码；正式/device合同仍按README。比较按JSON数据断言与按原始字符串断言，说明为什么字段顺序/换行不应造成误判。故意把Content-Type设置放到正文后，观察响应头再恢复。

源码先看Encoder.Encode怎样向Writer写数据，重点是error出口和末尾换行；字段发现机制可等结构体理解更稳再追。C#对照JsonSerializer时注意属性、字段、命名配置及忽略规则不同，不机械翻译标签。

## 与本题相连的原理和工程做法

### 一组数据：结构体、切片、map

~~~go
// 示意：这些类型定义放在函数外。
type Device struct {
    ID      int64  `json:"id"`
    Name    string `json:"name"`
    Enabled bool   `json:"enabled"`
}
~~~

结构体把相关字段放在一起；JSON 标签告诉编码器外部字段叫什么，它不是变量声明。`[]Device` 是设备切片；`map[string]Device` 用字符串找设备。`for _, device := range devices` 遍历切片；下划线表示忽略这次不需要的下标。

读取 map 时常用 `device, ok := byName[name]`。ok 用来区分“没有这个键”和“这个键对应一个零值”。nil map 可以读，但不能直接写入；需要先 make 或使用字面量创建。普通 map 的并发读写必须有同步措施。

切片由底层数组及描述信息支持。复制切片变量不等于复制所有元素；多个切片可能共享数据。保存历史报告时若还引用同一份可变数据，后来修改设备可能影响“历史”。业务上需要复制必要字段或序列化为独立快照。

### 本题的HTTP合同与数据流

本题约定 GET /device 返回200和一台固定假设备的JSON：name为sw-core，ip为192.0.2.10。Content-Type是application/json，可带charset；IP只是文本，不连接真实设备。

数据沿“结构体值→JSON编码器→w→HTTP响应正文”流动。Go字段Name要导出，标签把外部字段名固定成name；两者的大小写规则不同。先设置响应头，再编码正文；开始写正文后再改头通常已经来不及。

检查的是JSON字段和值，不是字段排列或空白。编码器返回的error属于Go调用结果；编码出来的数据才是HTTP正文。写出响应失败时记录错误，不把已经写出的半份JSON当成还能随意重发的完整响应。

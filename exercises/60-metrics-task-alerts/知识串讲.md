## 本题在项目中的位置

HTTP 接收成功不代表任务完成，后台卡住需要被及时发现。

本题只推进这个结果：用任务完成与积压指标触发一条可行动的教学告警。

## 先复习已经用过的写法

复习计数、时间差、错误分类；Counter 重启会归零，不能直接拿当前值当速率。

## 这次新增的知识

SLI 是测量，SLO 是目标；告警必须能对应用户影响和后续动作。

## 带着项目问题读原理

### 日志、指标、追踪看的是不同问题

日志描述某次事件；指标描述一段时间的数量与分布；追踪描述一次请求跨步骤的路径。Grafana 常用于展示，Prometheus 负责指标采集与查询，Alertmanager 负责告警分组、抑制、路由等处理；这些名称不能互相代替。

Counter 适合累计请求数，Gauge 适合当前队列长度，Histogram 适合延迟分布。计数器重启后可能归零，通常看 rate/increase；不同实例的 P95 不能直接取算术平均，聚合方式取决于数据类型。

示意：应用暴露一个自定义指标 inspection_http_requests_total，下面表达各服务最近 5 分钟 5xx 比例，需要先实际实现该指标与标签：

~~~promql
sum by (service) (
  rate(inspection_http_requests_total{code=~"5.."}[5m])
)
/
sum by (service) (
  rate(inspection_http_requests_total[5m])
)
~~~

没有流量时分母为零，不能直接当成 0% 错误；告警要考虑最小样本与“没有数据”的含义。上述指标名称是本课程示意，不是框架自动提供的保证。

### 指标标签要控制数量

method、路由模板、状态分类通常是有限集合；user_id、request_id、原始 URL 查询参数会制造大量时间序列，增加内存与存储。标签不同组合会相乘，不是“多一个标签只多一点”。[Prometheus 指标与标签命名](https://prometheus.io/docs/practices/naming/)。

接口看请求量、错误率、延迟；数据库看连接等待、锁等待、慢查询、磁盘；Worker 看完成速率、失败、重试、最老任务年龄；模型看延迟、限额、费用与输出校验失败。CPU 低不能证明任务没有卡死。

### SLI、SLO 与告警动作

SLI 是实际测量，例如“5 分钟内完成的有效巡检任务比例”；SLO 是目标；错误预算是目标允许的失败空间。目标要区分 API 接收成功与任务真正完成，202 返回快并不意味着整个业务健康。

本课程可以先约定一个教学目标：合成任务 95% 在 30 秒内完成，统计窗口与输入规模固定。它是实验条件，不是生产承诺。告警必须写清影响、证据入口、第一步检查和负责人。

告警去重、持续时间、恢复、维护静默都需要设计。瞬时尖峰不一定需要叫醒人，但持续积压且影响用户需要明确行动。发布灰度时把旧版与新版指标分开，看增量变化。


## 把例子接回现有项目

采集任务完成数、失败数、最老任务年龄和 API 延迟，定义有限标签和单位；选 Prometheus/Grafana 教学组合，告警区分持续积压、正常恢复与无数据。通知使用本机接收器或界面，不发真实外部消息。阈值按合成负载约定。

### 输入如何走到结果

Worker 延迟→最老任务年龄增加→告警；恢复消费→年龄回落→恢复。

### 分步动手

1. 先确定固定负载与完成时间教学目标。
2. 暴露并核对指标，再配置看板和持续时间规则。
3. 延迟 Worker、恢复 Worker、停采集器三次独立实验。

### 读完后检验是否理解

先口述本题输入、需要改变的模块、权威数据在哪里、失败怎样被发现，再去 [需求与验收](README.md) 实现。讲义配置和表名是示意，先核对已有项目再使用；一处知识卡住可以单独练小片段，业务验收仍以实际运行证据为准。

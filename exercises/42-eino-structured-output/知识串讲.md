## 与本题相连的原理和工程做法

### Graph 为什么比一大段提示词更可检查

可以把分析分成“取快照→检索知识→生成解释→校验引用→保存结果”。每个节点有明确输入输出，校验失败就进入受控错误分支。Graph 不是保证答案正确的魔法，它让你能定位是检索、生成还是校验失败。

结构化输出包含 conclusion、evidence_ids、uncertainties、suggestions 等字段；先校验 JSON 结构，再校验 fact_id 真存在、属于当前报告、用户有权读取。模型返回合法 JSON 并不意味着内容真实。

RAG 是先检索，再把有关内容交给模型。检索范围要先按租户、权限、文档版本限制；向量相似不等于事实正确或有权访问。报告应能追溯所用知识来源和版本，索引更新后旧报告仍保留原引用。

### 认证、授权、审计是三件事

认证回答“你是谁”；授权回答“这个资源你能不能读或改”；审计回答“谁在什么时候对什么做了什么，结果怎样”。读取 /inspection-jobs/123/report 时只检查 token 合法还不够，还要检查 report 属于当前用户或租户。

租户不能由客户端随意填一个请求头就变可信。资源查询带上可信租户范围，缓存 Key 和消息任务也要保持范围；AI 检索同样受限。服务之间的身份与终端用户身份要区分，不能让“内部服务已认证”自动变成读取任何用户数据的权限。

日志中的 user_id、tenant_id 是审计线索，不是证明访问获准的机制。敏感正文、密码、token 不应进入普通日志；审计记录要有访问控制和保留策略。

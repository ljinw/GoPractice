## 标准库逐步读：服务端的r/w与客户端的Request/Response

同一个net/http包既提供服务端也提供客户端。第01题的w是响应写入器，第05题的resp是收到的响应对象；只有明确是哪种类型，才能知道应该使用字段还是方法。

### 把两端的位置画出来

~~~text
客户端：构造请求 → client.Do/Get → 收到resp → 读StatusCode、Header、Body
                         网络
服务端：收到r → handler(w, r) → 通过w写状态、头和正文
~~~

| 变量 | 常见类型 | 状态码怎么处理 |
|---|---|---|
| 服务端w | http.ResponseWriter接口 | WriteHeader(code)设置，接口无直接读取字段 |
| 客户端resp | *http.Response结构体指针 | resp.StatusCode读取对端返回的码 |
| 请求r或req | *http.Request | 描述请求，不是响应结果 |
| 测试记录器rec | *httptest.ResponseRecorder | 自己的Code或Result().StatusCode用于检查 |

变量名可改，类型合同不能混用。这正是为什么不能在服务端凭感觉找w.StatusCode。

### Client、Get、Do分别怎么用

~~~go
type Client struct {
    Timeout time.Duration
    // 还有Transport、重定向与Cookie等字段；此处省略。
}
func (c *Client) Get(url string) (*Response, error)
func (c *Client) Do(req *Request) (*Response, error)
~~~

Client是可配置、可复用的客户端。Timeout := 2 * time.Second表达两秒；time.Duration底层按纳秒计，不能把裸数字2当两秒。总超时包含获取响应头及读取正文等过程，读Body时也可能超时。

Get适合发GET；需要设置方法、请求头和正文时用NewRequestWithContext构造请求，再交给Do。Client不是“一个请求”，Request也不是“已经发出去的调用”。

~~~go
func NewRequestWithContext(
    ctx context.Context, method, url string, body io.Reader,
) (*Request, error)
~~~

构造请求会验证/处理输入，但尚未发送网络。ctx负责取消和时间预算，取消依赖实际调用链配合；基础轮先掌握Client.Timeout，下一轮再把context传进去。NewRequestWithContext与Do各自返回error，不能只查其中一个。

### 网络错误、HTTP状态、解码错误是三层

1. client.Get失败：可能连接拒绝、DNS/协议或超时；先处理err，不能马上用resp.Body。
2. err == nil：得到一个HTTP响应，可能200，也可能404/500；本题要显式检查StatusCode范围。
3. 状态符合预期：Body仍可能是坏JSON、被截断或读取超时；解码/读取的error仍需处理。

成功获取响应后安排Close。Body不是字符串，而是读取流；Decode/ReadAll会消费内容。读到EOF并关闭通常有利于连接复用；不要为了复用而无界读取任意大响应，实际业务还需明确大小预算。

### 完整小客户端：保留分层错误

保存为本题warmup/client/main.go；先启动已有03题服务，再运行go run ./warmup/client/main.go。它只访问写明的本机URL，不遍历地址。

~~~go
package main

import (
    "encoding/json"
    "fmt"
    "log"
    "net/http"
    "time"
)

type Device struct {
    Name string `json:"name"`
    IP   string `json:"ip"`
}

// fetch读取一份设备；调用者提供可复用客户端和获准教学URL。
func fetch(client *http.Client, address string) (Device, error) {
    resp, err := client.Get(address)
    if err != nil {
        return Device{}, fmt.Errorf("请求设备接口失败: %w", err)
    }
    defer func() {
        if err := resp.Body.Close(); err != nil {
            log.Printf("关闭响应正文失败: %v", err)
        }
    }()

    if resp.StatusCode < 200 || resp.StatusCode >= 300 {
        return Device{}, fmt.Errorf("设备接口状态异常: %d", resp.StatusCode)
    }

    var device Device
    if err := json.NewDecoder(resp.Body).Decode(&device); err != nil {
        return Device{}, fmt.Errorf("解析设备响应失败: %w", err)
    }
    return device, nil
}

// main负责最终展示；fetch不在每一层重复打印同一个错误。
func main() {
    client := &http.Client{Timeout: 2 * time.Second}
    device, err := fetch(client, "http://127.0.0.1:18080/device")
    if err != nil {
        log.Print(err)
        return
    }
    fmt.Println(device.Name, device.IP)
}
~~~

%w保留底层错误以便上层识别，%d在这里格式化HTTP状态码。Device{}是这个结构体的零值，失败时先看error，不把零值设备当成功数据。

defer func(){...}()是在当前fetch返回时运行一个无名字的函数，用来调用Close并检查结果；函数末尾的()表示调用，defer把实际执行延后。把这一层拆小：先理解defer resp.Body.Close()的生命周期，再理解为什么完整示例加一层函数检查Close错误。此示例Close失败只记日志，未把已经读取的设备改为失败；严格资源错误合同需要另外明确。

## 与本题相连的原理和工程做法

### 错误、defer、context：程序要能收尾

`value, err := call()` 接住两个返回值。error 是接口，常规成功路径返回 nil，失败路径返回描述原因的错误。`if err != nil` 是常见判断；不要通过匹配错误字符串决定业务分支，优先使用稳定错误类型或 errors.Is/As。

defer 注册函数返回前执行的清理，例如关闭文件、释放锁。它不是“这一行马上执行清理”；普通调用的参数通常在注册 defer 时求值。循环里反复 defer 可能把资源保留到整个函数结束，长循环要缩短资源作用域。

context 传递取消、截止时间及少量请求范围信息。它不会强行杀死不配合的函数：下游调用要接受 ctx，循环要检查取消。不要把它当可随意塞业务字段的全局字典。

**重复学习：** 本题第一次跟写函数；HTTP 再看函数被谁调用；SQL 再接收 error；事务再用 defer；Worker 再练 context；Eino 再看接口和泛型。每次只补当前用途。


### 超时是一份总预算

假设入口允许 3 秒，认证已花 100 毫秒，SQL 花 500 毫秒，下游 RPC 不应又独立等待 30 秒。将请求 ctx 向下传，再按步骤设置更短预算。预算数值来自业务目标和测量，文中的数字只是教学例子。

客户端复用 http.Client/Transport；成功获得响应后要关闭 Body，是否继续读完取决于响应大小和复用需求。服务端要明确读取请求头、空闲连接、写响应等超时；流式 SSE 与普通短请求需要不同策略，不能照搬一个短写超时。

客户端取消后，普通查询通常也应取消；已经可靠接收的后台任务应由持久化任务系统管理生命周期，不能简单挂在已经结束的请求 ctx 上。两者通过 job_id 关联，而不是依靠一个永不返回的 HTTP 请求。

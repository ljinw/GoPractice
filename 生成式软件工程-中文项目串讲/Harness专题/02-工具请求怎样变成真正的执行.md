# H02：工具请求，怎样变成真正的执行

## 先分开两件事

模型返回“调用 read_note，name为functions.md”，只是一个动作请求。真正执行的是你程序里的函数。这个区别很重要：模型会生成不合法参数、未知工具名，也可能在不可信资料诱导下请求越界操作。程序需要独立检查。

像网络控制器接收请求一样，收到一条要求不代表设备已经执行，也不代表该请求有权执行。系统必须在执行边界做出明确判断。

## 一个工具至少包含哪些信息

| 部分 | 教学例子 | 谁会用它 |
|---|---|---|
| 名称 | `read_note` | 模型提出调用，程序查找实现 |
| 描述 | 读取指定教学笔记 | 帮助模型选择 |
| 参数格式 | name必须是字符串 | 程序检查请求结构 |
| 执行函数 | 接收name，读取允许的数据 | 程序真正运行 |
| 输出约定 | 返回正文或明确错误 | 程序与后续模型解释结果 |
| 执行限制 | 只允许两份教学笔记 | 程序执行边界 |

名称和参数说明会进入模型请求；执行函数的代码通常不会因为注册工具就自动一起发给模型。模型知道“怎么要求调用”，程序掌握“怎样实际执行”。

登记工具可以先理解为把名字和实现存到一张表里。接到名字后查表，找不到就拒绝。DSH使用有作用域、策略和生命周期的工具服务实现这些能力，实际比简单映射更完整。

## 从原始参数到实际文件，中间检查什么

假设收到教学请求：

```json
{"call_id":"c2","name":"read_note","arguments":{"name":"functions.md"}}
```

第一步检查工具名是否已登记。第二步检查arguments能否按约定解析，name是不是字符串，有没有未知字段。第三步检查本次调用者是否允许访问这份资料。第四步检查取消、预算以及本次工具是否仍可执行。通过后才调用实际函数。

“参数是字符串”只证明形状符合要求。`../../other.txt`也是字符串，却可能超出目录范围。身份也不应由模型在参数里填“我是管理员”决定，应该由可信程序上下文取得。

我们的样例直接使用固定笔记名白名单和内存映射，避免真实路径解析问题。真正文件工具还要处理规范化路径、符号链接、并发替换等问题；简单拼接路径或只检查字符串前缀，不是完整的目录隔离。

## 工具结果怎样准确配对

结果要关联到工具请求，例如c2。否则同一批读取两个文件后，系统可能把A的正文误认为B的结果。工具名称相同也不能代替调用标识，因为同一工具可以被连续或并行调用多次。

结果还应区分正常与失败。文件不存在、参数格式错误、权限拒绝、超时和结果未知，后续处理方式不同。模型读到结构化错误后可以调整计划，但它无权改变程序的授权规则。

教学样例将错误作为明确的工具结果记入内存历史；若错误未被后续模型使用，也仍应出现在诊断记录里。记录什么、把什么交给模型，可以是不同选择，下一讲会解释。

## DSH的执行管线怎样读

这里的“管线”是请求依次经过几段处理逻辑，不是物理网络链路。核对版本中的共享工具流程包括执行前策略、不可被后续监听器放宽的guard、执行包装、执行后处理和最终结果观察。

| 阶段 | 可以解决什么问题 | 需要注意 |
|---|---|---|
| 执行前 | 允许、拒绝或要求审批 | 监听器顺序可能影响决策 |
| guard | 固定的所有者策略拒绝 | 后续处理不能把已拒绝改为允许 |
| 执行包装 | 计时、取消、超时或受控重试 | 具体插件必须真的启用 |
| 执行后 | 检查、替换或拦截结果 | 外部动作可能已经发生 |
| 最终观察 | 记录已确定的结果 | 观察不能假装撤销外部动作 |

一个值得记住的具体细节：该版本工具定义里的 `timeoutMs` 只是声明，执行超时需要对应策略包装。不能看见配置字段就认定工具会在期限到达时停止。这个结论来自该版本README的限制说明，不应推广到任意框架。

## 工具、Skill和MCP怎样区别

工具是可以由程序执行的能力。Skill通常是可复用的任务知识、说明或步骤，可能指导怎样选择工具。MCP是把工具等能力在系统之间暴露的一种协议方式。

三者可以配合：Skill说明怎样整理资料，Agent通过MCP发现的读取工具取资料。但说明文档不自动拥有执行权限，接入MCP也不自动意味着远端工具可信或没有副作用。

## 一次只做一个实验

用样例依次提交：正常文件名、不在白名单的名字、未知工具、多余参数。先预测哪个检查阶段会拒绝，再运行测试看结果。不要一次更改四个条件。

最后口述：如果模型请求“读取其他人的报告”，你准备在哪里取得真实身份，在哪里核对报告归属？提示词里的拒绝说明与执行函数里的检查分别起什么作用？

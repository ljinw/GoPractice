# H09：先能推演，再读真实源码

## 阅读源码要回答什么

初学最容易遇到的困难是：看到一个陌生类型，点进去又看到五个，最后忘了最初的问题。因此每次只写一个问题，例如“工具结果怎样回到下一次模型输入”。

我们先读自己能完整运行的标准库样例，再用相同问题进入DSH与Eino。样例是教学模型，不是把DSH复制成几十行，也不包含它的全部能力。

## 样例中的五个对象

| 名字 | 存什么 | 谁读取它 |
|---|---|---|
| Message | 角色、内容、调用标识等历史 | 假模型与执行循环 |
| Call | 工具名、参数和标识 | 工具执行函数 |
| Reply | 最终文字或工具请求 | 执行循环 |
| Model | 根据历史返回Reply的接口 | 执行循环 |
| Config | 最大模型步数与工具调用数 | 每次派发前检查 |

先不用把全部语法背下来。看到结构体，问字段存了什么；看到接口，问哪个具体实现提供方法；看到切片，问历史增加了哪一条；看到error，问谁处理它。

## 第一遍只读Run的正常路径

程序先建立用户消息。每次循环检查取消，调用Model.Next，保存模型回复，再分成最终回答和工具请求两条路径。工具请求通过executeTool得到结果，结果带上相同调用标识加入历史。下一次Next就能看到它。

Go里函数参数按值传递，切片值也按值传递；底层存储可能共享。样例每次向模型提供历史副本，减少假模型意外改写历史的机会。复制一层Message并不解决任意嵌套对象的深拷贝，本样例字段范围是受控的。

固定脚本根据历史里已经出现的结果推进，而不是按“第几次调用”无条件成功。因此工具返回错误时，它也会读到错误，无法凭空当作取得了正文。

## 第二遍读三个失败分支

第一，未知工具返回工具错误，不运行任何实际能力。第二，文件名不在固定集合中返回拒绝。第三，模型或工具次数达到上限，Run返回明确错误并保留已记录历史。

预先取消的ctx会阻止首次模型请求。样例也检查已取消后的模型返回值，防止一个不配合取消的实现迟到返回成功。对阻塞且不响应ctx的实现，Run不能强制终止它；这正是协作取消的边界。

程序默认只访问内存笔记，不读真实文件、不发模型请求、不执行命令。这样故障实验不会牵涉你的生产项目。

## 读TypeScript只补眼前需要的几种写法

`interface`描述一个对象应提供的结构；`async`函数返回异步结果；`await`等待一个Promise结算；`obj.method()`是调用对象的方法；`=>`可用来表达函数。先看谁给参数、谁接结果，再逐步补类型系统。

TypeScript的运行时与Go不同，不能把结构相似当作执行语义一致。例如Promise、Go goroutine和C# Task都有异步相关用途，但生命周期和调度方式不同。第一次只比较“调用者如何等待结果、取消怎样传递”。

## 用真实源码检验一个判断

如果你猜“工具定义里写了timeoutMs就一定能终止它”，先看工具README，再沿管线找谁读取这个字段及启用的策略。所核对版本明确把超时执行交给相应包装插件。你应修正原先的猜测，并记录配置前提。

这就是源码阅读的产出：一个原先模糊或错误的判断，被具体证据澄清。打开很多文件不是目标；知道下一次遇到类似问题去查哪里，才是可迁移能力。

## 怎样完成第一个独立小项目

先运行[样例README](../examples/miniharness/README.md)中的命令，再做三项变化：新增一份教学笔记；把需求换成另一类资料总结；让一个工具稳定失败，解释后续行为。

之后才能考虑把Model换成Eino实现，增加持久化，再逐步研究恢复与真实模型评估。每次记录你自己写了什么、用了哪些提示、实际验证了什么。原69题的验收仍按原需求单独完成。

完整源码链接、版本、文件哈希与验证范围见[来源核对](../来源核对.json)。下一次复习从自己最常误判的一条路径开始。

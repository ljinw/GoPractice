# H05：为什么把模型、工具和循环都做成插件

## 从一个具体修改开始

学习助手已经能读笔记。现在想增加“记录每次工具耗时”。最直接的做法是在每一个工具函数前后加计时。只有一个工具时不难；工具变多以后，容易漏加、重复记录，修改日志格式还得改很多地方。

另一种组织方式，是让工具执行在固定位置提供扩展点。计时插件在这里接入，其他工具作者不必各写一套计时逻辑。增加功能时，改动集中到了可讨论的位置。

DSH选择“所有部分都可以是插件”的架构，模型适配、会话、工具服务和默认执行循环也参与这种装配。插件并不只指装在成品上的小按钮，它也可以提供基础服务。

## 服务、提供者、使用者分别是谁

| 角色 | 在学习助手中的例子 | 它回答的问题 |
|---|---|---|
| 服务约定 | “怎样读取一份笔记” | 输入输出和失败是什么 |
| 提供者 | 内存笔记读取实现、磁盘读取实现 | 这次具体怎样做到 |
| 使用者 | read_note工具 | 向谁请求这项能力 |
| 装配 | 本次选择内存实现并挂上工具 | 当前运行哪些部分 |

把约定和实现分开，可以在不改全部使用者的情况下更换提供者。但两个实现必须满足可观察约定：同名方法并不保证权限、错误或取消行为一致。

Go接口与依赖注入也能表达类似思想。Cordis还进一步管理插件依赖、作用域、事件和清理，它不是把Go接口换成TypeScript语法这么简单。

## Cordis中的ctx先怎样理解

把 `ctx.tools` 理解为从当前插件上下文取得工具服务，把 `ctx.llm` 理解为取得模型适配服务。使用者按约定找能力，不必直接导入某个提供者的内部状态。

需要某项服务的插件可以声明依赖。依赖尚未就绪，就不能假装它已经可用。这比人工记住“必须先启动A再启动B”更容易集中管理。

作用域可以让某个Agent看到一组特定工具，而另一个Agent使用另一组。它组织注册和查找的范围，不自动提供操作系统进程、文件或网络隔离。插件如果拿到了高权限对象，仍可能产生高权限动作。

## 事件和Hook怎样区别

“工具执行结束了”描述已发生事实，监听者可以记录耗时或更新展示。“下一步是否可以进入”发生在动作前，处理器可能允许、拒绝或调整。前者偏向观察，后者参与决策。

Hook可以理解为程序在明确位置留出的插入处理机会。原课中的 `agent/pre-step` 就是下一步进入前的扩展点。下面是已核对接口形状的解释片段，不是完整可安装插件：

```ts
ctx.on('agent/pre-step', async (payload, next) => {
  const decision = await next()
  return decision
})
```

`ctx.on`登记处理器；字符串标出扩展点；`payload`承载本次信息；`next`是后续处理链；`await`等待它返回；最后把结果交回调用方。

这里不调用next，可能意味着后续链被短路。它不是像普通日志回调一样“想调就调”。具体事件采用哪种分发方式，要查其合同。Cordis有观察、串行、并行及可返回决策等不同模式，不能把所有事件都套用同一规则。

## 顺序为什么会改变结果

假设插件A把路径改成另一个目录，插件B检查路径是否允许。先B后A，检查的是旧路径；先A后B，检查的是最终路径。两种结果不同。

因此应尽量让关键约束在最终实际动作前仍然有效。DSH共享工具管线中的guard可以提供不可被后续监听器放宽的拒绝，但它需要实际注册和正确覆盖目标，不能因为框架存在guard接口就认定业务策略已经配置。

两个压缩插件也可能都觉得自己在减少输入量，合起来却删掉关键上下文。插件单独正确，组合后仍需要验证。这是为什么“全是插件”不会自动消除复杂度。

## 卸载插件究竟撤销什么

插件登记了工具和事件监听，卸载时应撤销这些注册，避免卸载后仍继续收到事件。Cordis的可清理effect机制用于管理这类生命周期。

但插件此前写入的文件、已经发送的通知和已安装的软件，不会因为撤销监听而自动恢复。注册清理与业务补偿是不同机制。正在执行的任务如何结束，也要看具体提供者和取消合同。

## profile和bundle：最后怎样组成一个产品

profile是一次应用运行使用的命名组合，bundle是包含插件配置和相应代码的分发单位。一个组合可以提供Web界面，另一个提供无界面执行；基础能力可以复用。

在所核对版本里，运行组合由若干有顺序的配置层形成。修改某一层可能替换整个配置行，因此更改前后要看最终有效配置，不能只看自己编辑的片段。

## 原课的大型应用增强：为什么先锁对象再交给模型

原课用画布说明接入已有应用的思路。用户选中两个图形，希望Agent调整布局。应用先确定本次只允许修改哪些对象，把对象转换成JSON等可交换表示，再让模型提出修改。模型拿到的是被提供的表示，不是自动拥有整张画布。

| 阶段 | 应用负责什么 | Harness可以参与什么 |
|---|---|---|
| 选择 | 取得对象标识与当前版本 | 建立本次任务与会话 |
| 准备 | 锁定范围、生成对象表示 | 组织模型输入与工具说明 |
| 提议 | 接收候选修改，检查对象范围与结构 | 模型执行、工具协作、过程记录 |
| 提交 | 确认本轮成功并应用合法结果 | 提供结束状态和相关事实 |
| 失败 | 解锁，保留原对象或报告部分效果 | 保存失败与停止原因 |

锁定选区不等于永远冻结整个应用。用户可以继续操作不冲突的对象。提交前还要考虑目标版本是否变化，禁止模型偷偷增加选区外对象。若动作已经应用，后续失败怎样处理仍需实际设计。

原课把预留的界面插入位置称作slot，例如插件能贡献按钮或面板。它是界面扩展约定；当前DSH具体客户端接口要按版本阅读，不能把原课名词直接当成当前可调用的方法。

## 生成式界面：点击怎样回到同一条执行链

生成一个漂亮棋盘只是展示。要真正下棋，用户点击的位置需要变成结构化动作，程序检查轮次和合法性，把新的棋局加入会话，再让模型选择下一步。模型返回走法后，程序再次校验，界面才更新。

这个双向过程也能用于资料选择卡片或参数面板。界面表达状态和用户选择，程序管理真实规则，Harness组织后续执行。生成的HTML或JavaScript需要在明确环境与权限下运行，不能因为页面来自模型，就允许它调用任意本机能力。

先用纸面走一次“选择资料卡片→程序检查范围→模型读取资料→界面展示结果”，就能看出界面、会话和工具如何协作。此处依据[原课第09讲](../原始讲义/正文文本/lect9.md)作解释，没有声称本次安装或运行了相应插件。

本阶段不要求写一个全套插件系统。先做一个工具表和一个计时包装，说明它们怎样协作。以后真有动态装卸、多作用域和不同产品形态的需要，再研究Cordis的完整能力。

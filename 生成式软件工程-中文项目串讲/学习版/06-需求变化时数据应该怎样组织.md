## 数据结构是在回答哪些业务问题

学习助手最初只保存报告正文。后来你想显示报告列表，又想知道用了哪些文件、谁创建的、是否生成完成。这时“用一个字符串保存所有内容”就开始不方便。

先列问题，再选字段：报告的稳定编号是什么？谁能读取？生成过程中显示什么？完成时间与创建时间是否相同？引用的是当前文件，还是生成时的那个版本？字段不是为了让结构体看起来专业，而是为了让程序能准确回答这些问题。

## 先认识一份有名字的数据

下面只是类型声明，放在 Go 文件的 `main` 函数外；它不是独立可运行程序。

```go
type Report struct {
    ID      string
    OwnerID string
    Status  string
    Text    string
}
```

`type` 声明类型，`Report` 是名字，`struct` 表示把几个有名字的字段放在一起。ID 是字符串字段，OwnerID 记录所有者标识；这些名字与业务含义由我们约定。创建一个 Report 不会自动替你检查所有者或保存数据库。

如果一个字段缺失会被当成零值，那么业务必须决定零值是否合法。空 Text 可能是仍在生成，也可能是生成失败，单靠空字符串无法区分，因此需要状态或更明确的数据表达。

## 当前状态和发生过的事情，各回答什么

假设一份报告经历：创建、开始生成、读取材料失败、重试、完成。

当前状态表可以快速回答“现在是否完成”。事件记录可以说明“为什么花了这么久、重试了几次、失败在哪里”。只保存最后一行 completed，就丢失了过程；只保存过程而每次重新扫描，也可能增加读取成本。

| 顺序 | 已发生的事件（教学命名） | 推导出的当前状态 |
|---|---|---|
| 1 | ReportCreated | 待处理 |
| 2 | GenerationStarted | 处理中 |
| 3 | ReadFailed | 处理中，存在失败记录 |
| 4 | GenerationRetried | 处理中 |
| 5 | ReportCompleted | 已完成 |

“投影”就是按规则读取这些事件，计算一种需要的表示。它可以得到当前状态，也可以得到界面时间线。投影不会再执行一次生成报告；那会把读取历史变成重复工作。

事件表的字段、持久化与并发规则必须设计，不能凭这张表就认为系统已经可靠。专题会进一步区分内存记录、落盘和实际外部操作。

## 为什么历史报告要记录资料版本

星期一的笔记说“函数还不懂”，星期三你把它改成“已经会了”。如果旧报告每次展示都重新读取最新笔记，它的出处就会悄悄改变。

可以在生成时记录文件标识、读取版本或内容摘要，以及用于判断的必要事实。需要完全重现时，还要保留足够的原始内容与规则版本。只有一个哈希值可以帮助比较一致性，却不能从哈希还原丢失的正文。

当前文件负责表达现在，报告快照表达生成当时。是否保存副本、保存多久，是具体产品需要决定的成本和用途问题。

## 两个人同时修改时为什么可能丢数据

甲乙都读到版本3。甲先改名称并保存版本4，乙随后把基于版本3的对象整体写回，就可能覆盖甲的改动。

一个做法是更新时要求“数据库里的版本仍是3”。只有匹配才更新并增加版本；不匹配则提示冲突，重新读取和决定。这个思路叫乐观并发控制。需要数据库语句和受影响行数等实际保证，不能只在界面上显示版本号。

事务适合把需要一起成功或失败的数据库操作组织起来。但数据库回滚通常不能撤回已经发出的通知、安装命令或远端动作。跨边界的处理要另外设计。

## 先用你能验证的最小数据

第一份练习可以只有 ID、状态和正文。需要解释来源时再增加资料信息；需要权限时再把身份和读取规则接上。逐步增加不等于忽略已存在的业务要求，要在本次范围内说清楚哪些能力尚未提供。

不要同时上多种数据库来弥补含义不清。先用纸面状态表和少量假数据验证：相同事件顺序，是否得到相同状态？未知事件怎样处理？重放会不会触发新的外部动作？

今天用五行事件解释一次报告生成。周末先用 Go 的切片保存事件并计算状态；文件和数据库可以在具备相应基础后接入。

## 九轮练习

1. **读与预测**：设备今天改名，昨天报告哪些字段应保持原样？写理由，不先设计表。
2. **正常变式**：给教学事实增加采集时间和来源编号，说明报告怎样引用它们。
3. **边界**：一项值为0、一项值缺失、一项采集失败，设计三种可区分的展示与数据含义。
4. **排错**：旧报告随新规则变化，列出要检查的数据来源、规则版本与是否重新计算。
5. **独立完成**：为“提交→采集→报告→通知”画四项状态清单，指出哪些失败能独立发生。
6. **源码**：阅读NetMon证据复核中的时间和来源冲突分支，只抄判断条件，不查询生产数据库。
7. **C#对照**：用Go结构体与C#类分别草拟采样值、采集时间、来源三字段；解释缺失与0怎样区别，记录哪些序列化细节尚未核对。
8. **间隔复习**：完成第08讲后，重新解释“保存历史”和“按新规则重算”为什么不同。
9. **迁移**：把对象换成配置备份，讨论设备名变化、旧文件路径和内容哈希分别属于什么事实；实际实现以当前代码和获准数据核对为准。

## 核对思路

历史快照的范围由用途决定，不能任意复制所有敏感数据。缺失、0、失败必须有不同语义。重放事件不应盲目重复外部动作。只有当这些约定明确，事务、锁和查询优化才知道要保护什么。

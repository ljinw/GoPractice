## 这次先把一件事想明白

你让 Agent 写一个功能，界面能打开，按钮能点，代码也没有报错。此时究竟能确认什么？能确认的只是刚才实际试过的那些行为。要判断功能是否满足需求，必须先把“应该怎样”讲清楚，再拿实际结果逐项核对。

这件事和网络排障很接近。交换机端口亮灯，说明物理链路有了某种连接状态；它不能直接证明业务可以登录。软件也是分层验证：程序启动、接口返回、数据保存、用户完成目标，分别需要证据。

本套讲义用一个“学习资料助手”作连续例子。它从指定资料中回答问题，最后可以保存学习报告。你可以先在纸面推演，不需要先会 Go。每一讲都会把这个助手推进一点，最后才回到 NetMon 的真实代码。它是新的教学案例，不会改变原有巡检练习的验收规则。

## 从一句愿望，走到可以检查的要求

你说：“帮我总结 Go 学习笔记。”这句话还留着几个空位：总结哪几份？多长？要不要指出出处？笔记里没写的内容能否补充？最后显示在聊天框，还是生成文件？这些空位会由实现者填上。Agent 可以填得很快，但填出的选择未必符合你的想法。

先把本次任务缩成明确要求：读取指定的两份笔记；按“已经理解、仍有疑问、下一步练习”三个部分输出；每个事实注明来自哪一份；材料没提供的信息写“尚缺资料”；本次先只显示回答，不创建文件。

现在才能写检查：材料 A 说“会声明变量”，材料 B 说“函数返回值还不懂”，结果应把后者列为疑问。若结果写成“已经熟练函数”，即使文章流畅也不合格。

| 这一步的名称 | 具体内容 | 留下什么 |
|---|---|---|
| 意图 | 想知道自己学到了哪里 | 用户原话 |
| 明确要求 | 用哪些材料、输出哪些部分、缺资料怎么办 | 可讨论的规则 |
| 实现 | 程序读取材料、调用模型、整理结果 | 代码和配置 |
| 验证 | 用已知材料检查实际结果 | 输入、预期、实际与差异 |

先理解这四件事，之后再认识它们的英文名字。名称本身不会帮你检查程序。

## 看一遍完整的检查过程

第一步，自己先写预期。第二步，提供固定材料。第三步，运行。第四步，把结果和预期比较。第五步，改变一个输入后再验证。

为什么要改变输入？假设程序把“三个部分”的文章写死在代码里，第一次测试可能恰好通过。把材料 B 改成“函数已会，错误处理不懂”，回答也应跟着变化。这时你才开始区分“程序在处理材料”和“程序碰巧输出了相似文字”。

再做一个失败例子：不给材料 B。系统应明确说明缺少它，或者询问是否只用 A。若它仍声称看过两份材料，就暴露了来源不可靠的问题。

这些检查不要求你预知每一个字。对于模型回答，更适合检查必须包含的事实、不能出现的内容、出处是否成立。对于确定的代码行为，例如文件不存在，应有明确错误，则可以检查精确结果。

## 产品进度和你的能力怎样一起增长

Agent 完成一个模块，可以算产品取得进展。你的能力进展则可以这样记录：“我能解释这个处理函数接收什么；我自己改过一个条件；我找到了失败分支。”两种进度分别记。

不要因为 Agent 一次生成了十个文件，就要求自己当天理解十个文件。今天选择其中一条短路径：收到问题、取得材料、返回结果。你能预测一次运行，就有了继续往下追的基础。

每次评估改动，先问三个问题：输入变了，结果应怎样变化？依赖失败，会向谁报告？这次运行会修改什么？这些问题会贯穿后面的测试、数据和 Harness。

## 接回你熟悉的 HTTP

假设用户点击“生成学习总结”。服务端可以先返回“任务已接收”，后台稍后才完成总结。因此界面上至少有“已接收、处理中、完成、失败”这些不同情况。接口返回成功，不代表总结已经生成。

以后遇到 HTTP 202，可以把它放回这个例子理解：请求被接收，后续工作仍需查询。遇到 200，也要看接口约定究竟表达什么。先搞清业务含义，再记状态码。

Go 处理函数里写日志、写响应和创建任务，是不同动作。日志里的“完成”若写在模型请求之前，它反映的是代码执行到了那里，不能证明模型处理成功。第05讲会继续拆开“返回值”和这些外部动作。

## 今天怎样读，周末怎样练

## 原源码练习所指的处理函数

下面第6轮的“上述处理函数”指旧NetMon教材定位中的 `backend-go/internal/modules/network/routes/multi_agent.go` 的 `handleCreateMultiAgentTask`。历史阅读记录说它涉及输入、用户身份、入队和HTTP响应；本次没有核实NetMon当前版本，实际路径或行为可能变化。

它采用Go原生HTTP处理函数的参数形状，普通返回值与通过响应写入器产生的结果分开。尚不熟悉Go时先读[第05讲](05-把完成条件写成调用约定.md)，再带着“用户从哪里取得、何时入队、哪里写响应”三个问题读当前代码。旧项目更多定位见[历史对照](../补充资料/NetMon历史对照.md)。

## 原有九轮怎样使用

以下保留原有练习。源码题涉及旧版 NetMon 定位时，要核对当前代码；Go/C#尚不熟时先口述同一行为，之后再编码。一次做当前一小步，不要求一天完成九轮。

## 九轮练习

1. **读与预测**：用自己的话写出“没有命中的也要日志”至少三个还未明确的地方。先写，不急着让AI补答案。
2. **正常变式**：把健康检查换成“查询某份教学报告”。写出成功响应中必须出现的三项内容及其来源。
3. **边界**：报告不存在、报告为空、报告属于别人，分别写预期行为。不要将三种情况都称为“没数据”。
4. **排错**：给定现象“日志200、客户端404”，列两个可能原因和各自需要的证据。先查实际写状态的位置。
5. **独立完成**：关掉本讲，为“提交巡检任务”写不超过十条验收要求，必须区分已接收和已完成。
6. **源码**：在 NetMon 只读打开上述处理函数，找到获取用户、入队、返回状态三个调用。记录符号名，不推断数据库内容。
7. **C#对照**：比较Go无返回值函数与C#的`void`方法。二者都可能写文件或响应；再说明为何ASP.NET返回`IResult`是另一种组织响应的方式。
8. **间隔复习**：完成第03讲后，不看本讲，把“添加日志”重新写成可验证要求。
9. **迁移**：把同样方法用于“AI生成巡检报告”，要求结论有来源、缺证能看见，模型失败不能显示完成。

## 核对思路

第1轮至少应触及路径与方法、日志字段、记录时机或次数。第4轮可能是日志状态写死、提前记录、记录的不是实际响应状态；仅凭现象不能判定具体根因。第5轮应包括重复提交、失败出口和状态查询，而不只是成功返回一段文字。

能独立说出一条正常情况和一条反例，就先停下来运行自己的最小练习。阅读完成不替你勾选原题验收。

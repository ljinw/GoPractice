# 第07讲：控制复杂度与阅读源码

对应原课：需求和架构②。[在线原文](https://jyywiki.cn/GSE/2026/lect7.md) · [本地原文](../原始讲义/正文文本/lect7.md)

你看到一个带指针、接口和回调的函数就感到累，并不奇怪：一句代码可能压缩了几层约定。本讲的目标，是学会每次只展开必要的一层，并理解为什么系统要分模块。

## 哪些复杂度不能删，哪些是自己加的

巡检任务要区分用户、设备、时间与证据，这些要求来自业务。即使改成纸面处理，仍需要知道查的是谁、哪台设备、什么时候。这类困难来自问题本身。

如果同一个设备编号在五个模块中用五种格式，或者相同权限判断复制了十遍，这些额外困难来自实现组织。架构的一项价值，是减少这类不必要的重复和不一致。

因此，“代码少”不是唯一指标。一个函数少了检查，看起来更短，却可能把责任转嫁给每个调用者。一个抽象增加了几行接口，却让三处调用共用同一失败约定，可能降低整体理解负担。

## 抽象必须有清楚的承诺

抽象（Abstraction）允许使用者依赖公开约定，不必每次展开全部内部细节。你调用日志方法时，通常不必先阅读操作系统的文件写入实现，但必须知道日志输出到哪里、会不会失败、是否会结束进程。

“不展开细节”不等于“没有细节”。如果API隐藏了关键差异，例如把未采到的数据说成正常，那么抽象就在误导。好的边界把暂时不用知道的实现藏起来，把影响调用者决策的失败和限制暴露出来。

可用一个问题评估设计：业务改一处，需要跟着修改多少地方？如果新增一种报告输出格式就要改设备采集、鉴权、数据库连接和所有处理函数，说明职责可能缠在一起。但这只是排查线索，仍需根据真实调用链判断。

## 用三层解释一次请求

处理层负责HTTP输入输出，取得已认证身份，并调用业务。业务层判断是否允许创建任务、该锁定什么范围、怎样处理重复请求。数据访问层负责实际查询和存储。

这并非任何程序都必须拆成三个文件。一个十行练习可以先放在同一文件中，但思考时仍能分清三类责任。等重复和测试需求出现，再提取明确的函数或模块。

NetMon里可以从路由处理函数追到任务服务，再追到仓储调用。只看到文件夹名称不能证明分层正确；需要看调用是否绕过业务判断、错误是否被上层处理。

## 接口怎样帮助测试

Go接口描述某个值必须提供的方法。例如一个“报告读取器”可以只要求按编号读取报告。业务层依赖这个能力后，测试时可以提供固定结果，不必连真实数据库。

下面仅为签名示意，不是完整可运行程序。`Report`需要由所在练习定义，真实返回规则也需要明确。

```go
type ReportReader interface {
    ReadReport(id string) (Report, error)
}
```

`type`声明类型；`interface`定义方法集合；`ReadReport`是方法名；`id string`是输入；`(Report, error)`表示返回两个结果。调用者需要同时处理报告与错误，不能只看报告是否有字段。

一个具体类型提供了满足要求的方法，就可以实现该接口；Go通常不需要另写`implements`。C#通常在类声明中显式列出实现的接口，方法返回多个结果和错误的组织方式也可能不同。共同思想是依赖能力合同，具体语法分别学习。

在NetMon的Eino引擎中，`UnderstandingGenerator`接口声明生成理解结果的能力，构造引擎时接收它。它让编排代码可以依赖明确能力，而不是在每一处直接拼供应商请求。具体测试替身怎样接入，要查看对应测试。

## 源码阅读只追一条问题

第一步先写问题，例如“这个函数为什么不能返回字符串给HandleFunc”。第二步找完整签名。第三步找一处真实调用，观察参数从哪里来。第四步读直接使用参数的分支。第五步回到原问题，用自己的话解释。

暂时看不懂的辅助函数先记成一个合同，例如“验证输入并返回错误”。只有当当前问题依赖它的细节，才继续展开。你不需要打开仓库后从第一行一路读到最后。

源码笔记至少写版本、文件、函数和观察。文件行号会随修改变化，函数名是更稳定的定位线索。看到注释和实现不一致时，不能只相信注释；记录差异，检查运行证据。

## 框架限制是一种交换

框架提供路由、依赖装配或任务编排，同时要求你按它的接口表达问题。接受约定后可以复用能力；如果当前需求与约定冲突，就要评估适配成本。换框架并不会自动修复模糊需求或丢失的权限检查。

因此，学chi、gin和Eino时，可以先问：这个框架替我接管了哪一步？我仍负责哪些错误与业务规则？这能把原生库知识迁移过去，而不是重新背一套函数名。

## 原课提到的几种架构，用你熟悉的事情理解

UNIX工具组合强调小工具通过约定交换数据。例如读取日志、筛选请求、统计错误可以由不同步骤完成。组合容易成立，是因为输入输出约定清楚；前一步的输出格式突然改变，后一步仍可能解析错误。看到一条管道时，应追数据怎样流动，而不只是记命令。

关系数据库让你描述需要的数据，具体怎样读取交给数据库执行计划。这样能减少业务代码对物理存放方式的依赖，但索引、事务和查询成本仍然影响结果。抽象提供便利，同时留下需要理解的边界。

互联网协议允许不同系统遵循共同约定协作。你熟悉网络后，可以把这种经验迁移到软件接口：字段名称、编码、超时和错误含义都要说清。端口能连接，只证明某一层可达，不能证明上层业务理解一致。

MVC把业务模型、展示与处理输入的职责分开。它不能简单理解成每个页面对应一段SQL：如果同一业务规则散在几个页面处理器里，改规则仍会漏。MVVM进一步关注界面状态怎样与展示关联，在C#界面框架中很常见；这里先比较思想，不假定你已经会某个UI框架。

以任务按钮为例，“已提交”由请求接收结果决定，“正在执行”由任务状态决定，“报告可读”由结果事实决定。把它们都绑定到一次按钮点击上，就会把未来期待误当成已经发生。你现在不必开发前端，但可以用这三个状态检查界面文案是否真实。

原课的架构例子共同提醒我们：有价值的抽象提供一组可组合的规则，同时要求明确哪些事实、当前状态和未来决定不能混在一起。理解一种结构怎样降低修改成本，比同时学习许多框架更容易迁移。

## 九轮练习

1. **读与预测**：把“设备必须属于当前用户”和“同一权限逻辑复制三遍”分别归类，解释哪些复杂度来自业务。
2. **正常变式**：为日志增加请求编号，画出编号生成、传递、输出三个位置，判断哪些地方真正需要修改。
3. **边界**：一个抽象只返回“成功/失败”，却隐藏“部分数据缺失”。说明调用者会作出什么错误判断。
4. **排错**：同一请求在不同入口得到不同权限结果，先找重复规则与真实调用链，不立即更换框架。
5. **独立完成**：把“读取报告并返回HTTP响应”拆成三个职责，写输入输出和失败处理，不要求先拆文件。
6. **源码**：阅读NetMon `UnderstandingGenerator`声明、`NewEinoEngine`入参和一次`generator.Generate`调用，回答谁提供实现、谁调用能力。
7. **C#对照**：草拟对应的报告读取接口，说明显式实现、返回对象与异常/结果类型的选择，避免直接照搬Go双返回值。
8. **间隔复习**：读完第09讲后，再只用三分钟定位上述接口的调用，不通读整个包。
9. **迁移**：选择原练习20题chi或22题gin，解释框架处理函数与原生HTTP处理函数怎样连接。前置基础未完成时只读需求，不提前迁移作业。

## 核对思路

接口的价值要落在替换、复用或验证上，不是因为项目大就给所有类型配接口。判断职责时看输入输出、规则所有者和失败出口。源码阅读的成果是回答了一个问题；打开许多文件不等于理解更多。

原讲义还有枚举、归纳、约束解空间和具体架构案例。可以在自己遇到重复修改之后回读，它们会比单纯记住定义更容易理解。

## 把看不懂的长调用拆成几段

你看见 `reader.ReadReport(ctx, id)` 时，不需要立即通读整个仓库。先问：reader 是谁提供的？ctx 和 id 从哪里来？返回什么？调用后是否修改数据？这四个问题通常能帮你找到第一条可追踪路径。

我们继续做学习助手。最开始，把读资料、调用模型、保存报告都写在一个函数里也能演示。随着需要替换模型、补测试和处理失败，这个函数会越来越难改。分开职责的价值，是让一类变化尽量影响有限位置。

## 先用具体变化证明为什么要抽象

假设原来调用供应商甲，现在要换供应商乙。如果业务处理函数到处拼甲的请求格式，切换时就要改很多位置。可以让业务只依赖“根据消息生成回答”这一能力，再用一个适配实现处理甲的实际接口。

适配器就是做这种转换的代码：接收本系统的输入，转换成外部接口需要的形式，再把外部结果转换回来。它必须处理真实差异，例如不支持工具调用、错误格式不同或取消语义不同；不能只改一个地址就宣布等价。

抽象是在调用者和实现之间写清承诺。调用者知道怎样使用能力，实现者负责兑现它。承诺隐藏部分细节，但应保留影响调用者决策的失败与限制。

## Go 接口在这里表达什么

下面是教学签名，不是可独立运行的完整代码；`context` 来自标准库，声明放在函数外。

```go
type TextGenerator interface {
    Generate(ctx context.Context, question string) (string, error)
}
```

含义是：任何能提供这个 Generate 方法的值，都可以充当 TextGenerator。它接收取消/期限信息和问题，返回字符串与错误。具体是谁实现，交给创建对象的地方选择。

先注入一个始终返回固定文字的假实现，业务就能在没有真实模型时测试错误处理和接线。固定答案只能验证程序流程，不能证明真实模型回答质量。

接口本身不会自动创建实现，也不会保证实现正确响应取消。你还要找到具体方法和装配位置。C#常在类型声明处显式写实现关系，Go通常由方法集合满足约定；学习时比较相同职责，不机械逐词翻译。

## 三层职责可以先在一个文件里辨认

| 职责 | 接收什么 | 负责判断什么 | 交给谁 |
|---|---|---|---|
| 输入处理 | HTTP请求或命令行参数 | 格式是否可解析 | 业务函数 |
| 业务 | 当前用户、资料范围、任务 | 是否允许、怎样推进 | 资料读取与模型等能力 |
| 外部访问 | 已明确的读取或调用请求 | 实际I/O及协议错误 | 业务返回结果 |

不必为了三行代码先建三个目录。但要看出身份检查在哪里、错误由谁处理。文件夹叫 service 并不能证明所有业务判断都真正经过它。

## 怎样只追一层源码

先确定一个问题，例如“为什么工具超时没有停止文件读取”。找到配置读取位置，检查配置有没有被执行层使用，再追到读文件函数是否接收取消信号。每次只追当前问题需要的一条调用。

遇到未知辅助函数，先记它的输入输出约定；只有当前结论依赖其内部细节时才继续展开。这样不是回避原理，而是避免同时打开十个未知问题。

笔记写版本、文件、符号、输入、结果与尚未确认的分支。只看到了函数声明，就写“已定位声明”；看过实现，才写“已阅读”；运行过实验，再写实际观察。三种证据分别记录。

## 控制复杂度也包括拒绝当前不需要的结构

如果一个小助手只有本机使用，不需要为了学习 Eino 先拆成多个微服务。分布式会引入网络失败、协议版本和部署协调，值得在确有需求时研究。

反过来，把所有检查删掉也不等于简单。权限、来源和未知结果是业务真实存在的问题，需要给它们合适的位置。目标是让你能解释变化影响什么，而非单纯追求文件少或模式多。

今天读一个接口和一次真实调用。周末用假实现替换一次外部访问，确认业务测试仍能运行；之后再回到 Eino 和 Harness 的服务边界。

## 原有九轮怎样使用

以下保留原有练习。源码题涉及旧版 NetMon 定位时，要核对当前代码；Go/C#尚不熟时先口述同一行为，之后再编码。一次做当前一小步，不要求一天完成九轮。

## 九轮练习

1. **读与预测**：把“设备必须属于当前用户”和“同一权限逻辑复制三遍”分别归类，解释哪些复杂度来自业务。
2. **正常变式**：为日志增加请求编号，画出编号生成、传递、输出三个位置，判断哪些地方真正需要修改。
3. **边界**：一个抽象只返回“成功/失败”，却隐藏“部分数据缺失”。说明调用者会作出什么错误判断。
4. **排错**：同一请求在不同入口得到不同权限结果，先找重复规则与真实调用链，不立即更换框架。
5. **独立完成**：把“读取报告并返回HTTP响应”拆成三个职责，写输入输出和失败处理，不要求先拆文件。
6. **源码**：阅读NetMon `UnderstandingGenerator`声明、`NewEinoEngine`入参和一次`generator.Generate`调用，回答谁提供实现、谁调用能力。
7. **C#对照**：草拟对应的报告读取接口，说明显式实现、返回对象与异常/结果类型的选择，避免直接照搬Go双返回值。
8. **间隔复习**：读完第09讲后，再只用三分钟定位上述接口的调用，不通读整个包。
9. **迁移**：选择原练习20题chi或22题gin，解释框架处理函数与原生HTTP处理函数怎样连接。前置基础未完成时只读需求，不提前迁移作业。

## 核对思路

接口的价值要落在替换、复用或验证上，不是因为项目大就给所有类型配接口。判断职责时看输入输出、规则所有者和失败出口。源码阅读的成果是回答了一个问题；打开许多文件不等于理解更多。

原讲义还有枚举、归纳、约束解空间和具体架构案例。可以在自己遇到重复修改之后回读，它们会比单纯记住定义更容易理解。

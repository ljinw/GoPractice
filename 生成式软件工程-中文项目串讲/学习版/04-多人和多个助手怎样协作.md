## 两个看起来都正确的改动，为什么合起来出错

学习助手原来用 `file` 字段表示文件名。你让一个 Agent 把接口字段改成 `path`，另一个 Agent 给读取函数补测试。第一个改了调用者，第二个仍按 `file` 写新逻辑。各自在自己的输入里可能通过，合在一起却取不到参数。

协作的问题不只有“同一行被两个人修改”。即使没有文本冲突，接口含义、状态和前置条件也可能冲突。这种情况需要组合后的行为测试才能发现。

## 分支到底保存什么

分支可以理解为指向某条提交发展线的名字。新建分支时，不等于自动复制一台独立电脑。你切换当前工作目录的分支，通常是在同一目录展开另一份提交状态。

多个 Agent 如果同时操作同一个工作目录，即使约定分支不同，仍可能互相影响。独立工作目录或 worktree 能隔离文件编辑，但数据库、端口、缓存和外部服务也需要分别安排。文件隔离不自动等于所有运行资源隔离。

本讲先在纸面画三条变化线：共同起点、你的改动、另一个人的改动。合并要把两边变化组合成可解释的新状态，不是只把两个文件机械拼起来。

## 看一个没有文本冲突的例子

| 位置 | 甲的改动 | 乙的改动 | 合起来的风险 |
|---|---|---|---|
| 请求处理 | 字段改成 `path` | 未修改 | 上游提交新字段 |
| 读取函数 | 未修改 | 继续读取 `file` | 下游仍期待旧字段 |
| 单独测试 | 用新处理函数的假依赖 | 用旧字段测试读取函数 | 两边单测都可能绿 |
| 集成测试 | 真正把两者接起来 | 同一实际请求 | 可以发现接线不一致 |

定位时先保留失败请求，再追字段在哪一步改变。不必一开始就在全部文件中找“谁写错了”。

## 锁定为什么有用，为什么还要检查旧结果

假设一个任务正在生成 `report.md`。系统给任务分配一段执行资格，避免两个执行者同时写同一目标。进程失联后，资格可能到期，允许新的执行者接管。

但旧进程可能只是暂时卡住，稍后又继续写。如果提交结果时不核对资格，旧结果仍可能覆盖新结果。因此“拿过锁”和“此刻仍然有权提交”也要区别。

初学时可先用一个整数版本理解：任务从版本3推进到版本4，提交者还拿版本3就应被拒绝。这是教学简化；真实数据库、租约和分布式协调有自己的实现条件。

## 多 Agent 怎样分工才可检查

先把共享约定写清：输入输出、谁改哪些文件、谁拥有数据、怎样测试、什么情况下停止。一个负责实现，一个负责审查，也需要审查者看到需求、差异和验证证据。

两个模型给出相同答案，不自动形成独立证据。它们可能看了同一份错误材料，也可能都没有运行代码。真正的复核需要能提出反例、核对来源或执行有效检查。

多 Agent 会增加协调开销。一个短小功能用单 Agent 加人工检查可能更容易理解；等任务真的可拆分，再比较并行带来的收益。角色数量不是完成质量的指标。

## 合并之后还需要什么

先读最终差异，再跑组合后的检查，确认依赖版本、配置与接口仍一致。审查记录写“验证了哪个输入”，比“甲乙都说没问题”有价值。

Go 和 C# 都会遇到接口协作、分支与共享状态问题；换语言不会消除它们。本讲不要求同时写两门语言。先能解释 `path` 从请求走到读取函数的路径，再对照另一种表达。

今天可以用两个纸面改动模拟字段变化；周末在独立仓库做一次小合并。遇到冲突先说明两边分别想保留什么行为，再决定最终代码。

## 原有九轮怎样使用

以下保留原有练习。源码题涉及旧版 NetMon 定位时，要核对当前代码；Go/C#尚不熟时先口述同一行为，之后再编码。一次做当前一小步，不要求一天完成九轮。

## 九轮练习

1. **读与预测**：甲改状态名、乙改按钮判断，各自测试通过后合并。预测用户会看到什么，并说明为什么Git未必报冲突。
2. **正常变式**：一人改日志文案，一人改数据库查询；列出它们可以独立推进的条件和仍需共享的约定。
3. **边界**：两个工作目录使用同一测试数据库，列出可能干扰的两个结果。
4. **排错**：测试昨天通过今天失败，先确认代码版本、运行目录、配置和测试数据，再判断是否为业务缺陷。
5. **独立完成**：为两个助手写一份简短协作约定，包含修改范围、共同接口、交付证据和整合检查。
6. **源码**：只读查看NetMon `module.go`中恢复协调器的启动，以及`persistent_agent_recovery_service.go`的循环。找出“程序启动”和“恢复任务”之间的调用。
7. **C#对照**：解释一个进程里的`lock`为什么不能默认阻止另一进程领取同一任务；再把问题换成Go互斥锁。
8. **间隔复习**：完成第06讲后，重新区分文本冲突、业务冲突和运行资源冲突。
9. **迁移**：将协作对象换成“AI生成报告”和“人工修订报告”。说明哪些内容允许覆盖，哪些应该保留版本或追加修订。

## 核对思路

好的协作约定应说明谁维护状态定义，如何检查接口变化，以及多个结果整合后由谁验证。锁与隔离目录都是工具，不能代替共享语义。生产历史和用户工作不用于演练破坏性操作；Git操作练习另用教学仓库。

本讲的通关依据是能指出一个“没有文本冲突但业务出错”的例子，并设计能发现它的检查。无需背诵所有版本管理术语。
